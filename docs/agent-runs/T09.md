# T09: Per-tab URL routing and deep links

## Objective

The dashboard's sixteen tabs were React state, wouter routed exactly one path,
and section deep-linking travelled over a window `CustomEvent`. None of the
three produced an address, so the output of using the tool — a conversation with
a client about a specific finding — could not be linked to. The task was to give
every tab a real route at `/tab/:tab` with an optional `#section` fragment, to
define the tab identifiers once and derive both the router and the sidebar from
that definition, to handle `/` and unknown tabs deliberately, to replace the
`CustomEvent` with navigation, and to do all of it without losing either the
`visitedTabs` keep-alive behaviour or the per-tab lazy chunks.

This is backlog 6.3.

| File | Reason |

## Decisions and trade-offs

### `/` redirects rather than renders

`/` redirects to `/tab/overview`, with `replace`. Rendering the default tab at
`/` would have worked too, but then the same view would have two addresses and
the address bar would show the one that names nothing — which defeats the point
of the task, since the URL a reader copies is usually the one they are looking
at. `replace` rather than push, because `/` and `/tab/overview` are the same
view and a back button that walked between them would be a step that appears to
do nothing. The cost is that back from the first tab leaves the application
immediately; that is correct for an entry point.

`/tab/nonsense` redirects the same way, also with `replace`, so a bad link
cannot leave a reader on a back button that bounces them between the bad URL and
the default tab. The redirect is decided in the route table rather than inside
the dashboard, so an unknown tab never mounts the shell at all. Genuinely
unknown paths such as `/tab/intune/extra` still fall through to `NotFound`.

### How `visitedTabs` was preserved

`visitedTabs` mounts a tab on first visit and then leaves it in the DOM, hidden,
so returning to it neither remounts the tree nor refetches. Two things had to
hold for it to survive routing.

First, `Dashboard` must not remount when the tab changes. wouter's `Switch`
returns `cloneElement` of the same `<Route>` element for every path the pattern
matches, and the route's children function returns the same component type, so
React reconciles rather than remounts. That is the reason the tab lives in one
`/tab/:tab` route rather than sixteen routes: sixteen routes would put a
different element in `Switch`'s single child slot per tab and remount the shell
on every click.

Second, the set has to grow in the same render that reveals the tab. The active
tab now comes from the URL rather than from a state setter, so there is no
handler in which to batch the two updates. Growing the set in an effect would
commit one frame in which the tab is active and its panel empty, a visible
blank. Setting state during render instead — React's documented pattern for
adjusting state when props change — makes React re-run the render with the
grown set before committing anything, so the mount and the reveal land together.
Verification 4 measures the result directly rather than trusting the reasoning:
the filter text survives, the DOM node is identity-equal across the round trip,
and the server sees no second request.

I also froze the panel elements at module scope. React skips re-rendering a
subtree when handed the same element object, so a tab change no longer
re-renders every mounted-but-hidden tab. This is not required for keep-alive —
the old code re-rendered them all on every click — but it is a large amount of
avoidable work on the chart-heavy tabs and the routing change was the moment to
remove it.

### Anchors rather than buttons in the sidebar

The sidebar entries are wouter `<Link>`s, so they render real `href`s. For a
tool whose purpose is to produce a link to a finding, being able to right-click
a section in the sidebar and copy its address is most of the value. The cost is
one special case: clicking the link the URL already points at changes no
location, so nothing would re-open or re-scroll, where the old event did so
unconditionally. That case clears the fragment and restores it on the next
frame, both with `replace`, so the round trip leaves no entry in the back
history.

### The section decides, not the dashboard

The old design had `Dashboard` dispatch an event to open a section and
separately retry `document.getElementById` up to ten times to scroll to it.
Both are gone: a section reads the fragment itself, and scrolls via a ref
because by the time its effect runs it is mounted by definition. That covers the
case the retry loop existed for — a deep link into a tab whose chunk has not
downloaded yet — more directly than the loop did.

I checked before removing anything that this loses no behaviour. The old scroll
worked on any element carrying the id, while the new one only works for a
`CollapsibleSection`, so I resolved all 55 ids in `NAV_SECTIONS` to their
definitions. Every one is a `CollapsibleSection`, including the two built from
template literals (`framework-${fw.framework}`) that a plain grep misses.

The subscription's snapshot is the boolean "does the fragment name me" rather
than the fragment itself, so a navigation re-renders only the one or two
sections whose answer changed rather than every section on the page.

### Back and forward are served by a document navigation

This is the significant compromise in the change, and it is a workaround for a
defect rather than a design choice.

Rendering the dashboard in response to a `popstate` sends React into a render
loop it never leaves. The URL updates correctly and then the page stops
responding to anything at all — not slow, stopped, with a pause taken at the
time showing React spinning in its own work loop. I confirmed it in an ordinary
browser window as well as headless, so it is not an artefact of the harness.

What I established by bisection, each case in a fresh browser:

- It reproduces if and only if the Intune tab is mounted, whether it is the
  visible tab or a hidden one. `settings -> apps -> back` is fine;
  `apps -> intune -> back` freezes, and the destination there is the light tab.
- It does not reproduce for the identical tab change made by clicking. It is
  specific to the browser's own event, whose update React flushes inside the
  handler rather than after it.
- A `popstate` that changes nothing wouter reads (same path, different query) is
  fine, so the browser's traversal is not the problem; the React render is.
- Replacing the route component with a bare `<div>{tab}</div>` inside the same
  application, providers and router: fine. It needs the real dashboard.

What I ruled out as the cause, each by building and re-testing: the per-section
fragment subscription, the sidebar `<Link>`s, the frozen panel elements, the
browser's scroll restoration, the smooth-scroll animation, the
`refetchInterval` closure on the collection-status query, `useDeferredValue`
around the tab, and holding the tab a task behind the URL.

That leaves the cause inside `pages/tabs/IntuneTab.tsx`, which this task may not
change beyond how it navigates. So it is contained rather than fixed:
`popstate` and `hashchange` are intercepted in `App.tsx` before wouter's
listeners see them, and the page reloads onto the entry the reader asked for.
Back and forward therefore walk tab history correctly and never freeze. The
cost is that they reload rather than transition, so a traversal loses the
visited-tab cache; clicks and deep links are untouched and stay instant. The
comment above it carries the reasoning and the one-line test for whether it is
still needed.

I would rather have shipped the real fix. Given the choice between a router
whose back button freezes the application and one whose back button reloads, the
reload is plainly right, and leaving the defect undocumented would have been
worse than either.

## What I did not do

- **I did not fix the underlying render loop**, because it is in `IntuneTab.tsx`
  and the brief allows changes to a tab component only to how it navigates. The
  containment above is in a file I own. Everything I learned about it is in the
  section above and in the comment in `App.tsx`.
- **I did not add automated tests.** The dashboard package has no test runner —
  `pnpm run test` runs only `artifacts/api-server` — and test configuration is
  T12's. Adding one would have meant editing files I do not own. The
  verification below is therefore driven through a real browser instead, and
  T12 should be told these behaviours are worth a regression test.
- **I did not update `BACKLOG.md`**, which still describes the `CustomEvent`
  mechanism and cites line numbers that have moved. It is not in my file list.
  This is why verification 7 below is not literally empty.
- **I did not fix the pre-existing lint failure** in
  `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`, per the
  contract. It fails on arrival and still fails.
- **I did not set a per-tab document title.** A shared link shows the same title
  for every tab. It is a real gap for a link-sharing feature but not in the
  brief.

## Risks and follow-ups

### What a future tab author has to do (T11)

Adding a tab is now three edits, and the compiler names two of them:

1. Add `{ id: "your-tab", label: "Your Tab" }` to `TAB_ROUTES` in
   `src/lib/tabRoutes.ts`, in the position the sidebar should show it. This is
   the only place the identifier is written; the route, the href helper, the
   sidebar entry and the panel all follow from it.
2. Add the icon to `TAB_ICONS` in `Dashboard.tsx`. Omitting it is a type error,
   not a blank sidebar entry.
3. Add the `lazy(() => import(...))` entry to `TAB_COMPONENTS` in
   `Dashboard.tsx`. Also a type error if omitted. Keep the `import()` inline:
   pulling the component in with a static import at the top of the file is the
   one change that would quietly undo the code splitting, and the build's entry
   budget is the thing that would catch it.

Optionally add sidebar section links to `NAV_SECTIONS`. Each `id` must be the
`sectionId` or `storageKey` of a `CollapsibleSection` in that tab — the fragment
mechanism only opens collapsible sections, so an id on a plain element will not
open or scroll. Set `tab:` on the entry only when it points at another tab.

Nothing needs to be added to `App.tsx`.

### For a human to look at

- **The Intune render loop is unfixed.** It is the most important thing in this
  report. Until it is fixed, back and forward reload the page. The reproduction
  is one line: open `/tab/intune`, click any other tab, press Back, with the
  interception in `App.tsx` removed. I would start by bisecting `IntuneTab.tsx`
  itself, since the trigger is that the tab is mounted at all; the queries
  around `avdGroupId` and `getGetM365GroupDeviceMembersQueryKey` are the first
  thing I would look at, because a query key rebuilt on every render is a known
  way to make an external-store snapshot unstable, and an unstable snapshot is
  what makes React spin in the work loop the way the pause showed.
- **T12 should cover this behaviour with tests.** Direct load of a tab URL,
  the unknown-tab redirect, keep-alive across a tab change, and a fragment deep
  link are all cheap to assert once a runner exists, and all four are the kind
  of thing that breaks silently.
- **Per-tab document titles** would make a shared link identify itself in a
  browser tab and in a chat preview. Small, and squarely in the spirit of the
  task, but not in it.
- **Deployment outside the container.** `nginx.conf` already has the SPA
  fallback (`try_files $uri $uri/ /index.html`), so deep links resolve there and
  under `vite preview`. Anything serving `dist/public` without that rule will
  404 on `/tab/intune`, which was not a possible failure before this change.
- **The section deep link cannot express a filtered view.** The fragment names
  a section, not a row or a finding. Linking to an individual finding, which is
  what the brief's framing ultimately wants, would need query parameters the
  tabs read.
