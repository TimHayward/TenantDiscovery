# T05: Dependency and workspace hygiene

## Objective

The dependency manifests across this workspace did not describe what the code
actually needs. I was asked to correct that: reclassify the dashboard's
runtime dependencies out of `devDependencies` (where nearly all of them sat,
working only by accident of Vite bundling everything regardless of which
block a package is declared in), remove packages that are declared but never
imported, converge the duplicated CSV stack (`papaparse` and `react-csv`)
onto whichever one `ExportBtn` actually uses, tighten `express` and `cors`
off their major-only ranges, work out why `thread-stream` is pinned to an
exact patch version and either document or lift that pin, and add a
Dependabot configuration that keeps this from drifting again.

## Decisions and trade-offs

**The CSV library choice: `react-csv`, not `papaparse`.** The brief allowed
preferring `papaparse` "if the choice is genuinely open" on the grounds that
it both parses and generates, while `react-csv` couples a data concern to a
React component. I read `ExportBtn.tsx` (`artifacts/m365-dashboard/src/components/ExportBtn.tsx`),
the single call site the brief said centralises CSV export: it imports
`CSVLink` from `react-csv` and nothing from `papaparse`. A full-repo grep for
`papaparse` outside `package.json`/`pnpm-lock.yaml` returned nothing — no
call site anywhere uses it, in this dashboard or elsewhere in the repo. The
choice was therefore not open: `react-csv` is the one working, centralised
implementation, and `papaparse` was pure dead weight. `BACKLOG.md` line 102
independently confirms this was the intended resolution ("ExportBtn already
centralizes usage; pick its dependency and migrate the other's call sites").
Migrating `ExportBtn` to `papaparse` instead would have meant reimplementing
`CSVLink`'s blob-and-anchor download behaviour by hand for no functional
gain, so I removed `papaparse` and `@types/papaparse` and kept `react-csv`
and `@types/react-csv` (react-csv ships no bundled types, so the `@types`
package is still needed).

**`thread-stream`: re-ranged, not left pinned, on demonstrated evidence.**
`esbuild-plugin-pino`'s bundling code (`node_modules/.pnpm/esbuild-plugin-pino@2.3.3.../dist/index.js`)
does `path.dirname(require.resolve("thread-stream"))` and then hardcodes
`lib/worker.js` under that directory as the worker bundle's entrypoint. That
is a structural assumption about `thread-stream`'s internal file layout, not
a documented public API, which is exactly the kind of thing an exact-version
pin exists to protect against. Rather than guess, I tested it: bumped
`thread-stream` from the pinned `3.1.0` to the current `3.2.0` (the latest
3.x release, published 2026-07-29, comfortably past the 1-day
`minimumReleaseAge`), ran `pnpm install`, built the api-server with
`node ./build.mjs`, and ran the resulting `dist/index.mjs` for real. The
`pino-pretty` transport came up (`thread-stream-worker.mjs` and
`pino-worker.mjs` both present in the build output), `GET /api/healthz`
returned `200`, and the log output was correctly colourised, which only
happens if the worker-thread pipeline actually works — see Verification.
That demonstrates the exact pin is not needed for this specific version.
I did not, however, drop it to a full `^3.0.0` caret matching what `pino`
itself declares: I have only tested one version newer than the pin, and the
whole task's theme is *tightening* loose major-only ranges (`express`, `cors`)
because "the lockfile is the only thing pinning reality" — reopening
`thread-stream` to a caret would reintroduce exactly that problem for a
dependency with a real, demonstrated coupling to esbuild's bundling
internals. I used `~3.2.0` instead: tightened to the tested minor, patch
updates only, matching the same tilde treatment I gave `express` and `cors`.

**Where the `thread-stream` reasoning is documented.** The brief asks to
"document the reason in a comment next to the pin." `package.json` is
parsed as strict JSON by `npm`/`pnpm`, so no comment can live next to the
version string itself, and `build.mjs`, `README.md` and `BACKLOG.md` — the
only other files where this reasoning could naturally live — are not in my
file list. I have put the full reasoning here instead, which the brief
also explicitly asks for in this section. A reviewer who owns `build.mjs`
may want to add a short comment there pointing at this report; I did not do
that myself because it would mean editing a file outside my scope.

**Two `zod` findings that turned out not to be findings.** I checked
carefully whether `zod` or `@hookform/resolvers` were used anywhere in
`m365-dashboard/src/components/ui/form.tsx` before removing them, since that
file imports `react-hook-form` and shadcn's form scaffolding conventionally
pairs `react-hook-form` with `zodResolver`. It does not: `form.tsx` imports
only `react-hook-form`, `@radix-ui/react-label` and `@radix-ui/react-slot`.
`react-hook-form` itself stays classified as a dependency (moved, not
removed) because it genuinely is imported in `src/`, even though nothing in
the app currently renders the `Form` component that consumes it — the brief's
test is the literal import, not whether the importing file is itself
reachable from the app's entry point. Deciding whether `form.tsx` (and any
other unused shadcn scaffolding) is dead code worth deleting is a different,
riskier task than dependency-manifest hygiene and is not something I did.

**One root Dependabot entry per workspace package, not a single `"/"` entry.**
Dependabot has supported a single root `directory` for npm/yarn workspaces
for years, discovering nested `package.json` files automatically from the
`workspaces` field. Whether that auto-discovery reliably covers a
`pnpm-workspace.yaml`-defined workspace (rather than npm/yarn's
`package.json`-based one) is something I cannot verify from this
environment — Dependabot runs as a hosted GitHub service, not something I can
invoke locally. Rather than gamble that a single root entry would silently
miss `artifacts/*`, `lib/*` and `scripts`, I wrote one explicit `npm` entry
per real package directory (10 entries) plus one `github-actions` entry. The
trade-off is verbosity — 172 lines for what could in principle be a dozen —
against not silently under-covering the workspace. I validated the file
parses as well-formed YAML with the expected 11 entries (`js-yaml`, already
present in the dependency tree — see Verification) but could not validate it
against Dependabot's actual JSON schema or run it, since both require GitHub's
hosted service.

**`cooldown.default-days: 1` on every npm entry, as a recommendation the
brief asked me to flag rather than silently decide.** See Risks and
follow-ups below for the full reasoning; I implemented it as a concrete,
reversible default rather than leaving only prose, but it is explicitly
flagged there for a human to confirm actually takes effect, since I have no
way to observe a live Dependabot run from here.

**Patch-only grouping, not broader grouping.** The brief specifically asked
that "patch updates arrive as one pull request rather than thirty." I built
exactly that: one `patch-updates` group per directory entry, matching
`update-types: ["patch"]` against every package (`patterns: ["*"]`). Minor
and major bumps remain individual PRs, which is the conventional split
(patches are routine; minors and majors can carry behavioural changes worth
reviewing individually) and is what was actually asked for, not a broader
reading that would have bundled everything.

## Risks and follow-ups

**Dependabot and `minimumReleaseAge: 1440` will conflict unless someone
confirms `cooldown` actually mitigates it.** `pnpm-workspace.yaml` refuses to
install any package version published less than a day ago. Dependabot has no
knowledge of that setting and will happily open a PR for a package published
an hour ago; `pnpm install --frozen-lockfile` in CI would then fail on that
PR until the package ages out, which reads as a broken PR rather than a
timing issue unless someone already knows why. I added
`cooldown.default-days: 1` to every `npm` entry in `dependabot.yml`, which is
a real, documented Dependabot feature intended for exactly this — delaying a
proposed update until a version has existed for N days — and setting it to 1
day mirrors `minimumReleaseAge: 1440` precisely. I could not verify this
actually works end-to-end, since Dependabot runs as a hosted GitHub service I
cannot invoke from here. **A human should watch the first Dependabot run**
and confirm PRs it opens are for packages already past the cooldown window;
if `cooldown` turns out not to be honoured (e.g. the GitHub plan predates the
feature, or the schema is stricter than what I wrote), the fallback is either
removing `cooldown` and accepting that some Dependabot PRs will need to sit
unmerged for a day, or moving the whole `npm` ecosystem to a less frequent
schedule as a coarser mitigation. I've implemented what I'd recommend, but
per the brief this is flagged for a human decision, not treated as settled.

**Whether Dependabot's pnpm-catalog support (`catalog:` version specifiers)
is mature enough to handle this workspace cleanly is untested.** A large
share of the dependencies in `m365-dashboard`, `mockup-sandbox` and
`api-server` now use `"catalog:"` as their version string, pointing at
`pnpm-workspace.yaml`'s `catalog:` block rather than a semver range in the
package's own `package.json`. Dependabot added pnpm-workspace support
relatively recently; whether it correctly resolves and bumps `catalog:`
entries, or silently skips them, or errors, is something only a live run
against this repository can answer. Worth watching the first scheduled run
for parse errors or a `Dependency Graph` tab warning on the repository.

**Ten `npm` entries in `dependabot.yml` is verbose and will need trimming if
`lib/integrations/*` (referenced in `pnpm-workspace.yaml`'s `packages` glob
but not yet populated) gains real packages.** Not urgent, just noted so it
isn't missed later — a new workspace package under `lib/integrations/` will
need its own `dependabot.yml` entry, since I did not use a wildcard root
entry.

**`BACKLOG.md` lines 100-103 are now stale.** They describe exactly the
dashboard-misclassification, CSV-convergence and `cookie-parser`/`thread-stream`/
range items this task closes. `BACKLOG.md` is not in my file list, so I have
not edited it; a human should mark those lines resolved.

**`build.mjs` would be the natural home for a comment about the
`thread-stream` coupling to `esbuild-plugin-pino`'s internals**, once
someone who owns that file is doing other work near the pino plugin
configuration (line 109). I left the full reasoning in this report instead,
per the file-ownership boundary; it is easy to lose track of an undocumented
coupling like this over time, so I'd suggest linking to this report from a
one-line comment there when convenient.

**Two `zod` sightings worth a second look, not touched here.** `zod` is
declared correctly as a `dependency` (via `catalog:`) in `lib/api-zod` and
`lib/db`, and in `api-server`, where it is genuinely used. It was only
removed from the two frontend apps, where it was never imported. This is not
a risk, just worth stating plainly since "zod: removed" and "zod: kept" both
appear in this report and could look inconsistent at a glance.
