# T07: Shared UI kit and sandbox quarantine

## Objective

`artifacts/mockup-sandbox` carried a second, parallel copy of the dashboard's 55-file shadcn
component set, and sat in the workspace where CI typechecked and built it on every push. The task
was to establish precisely where the two copies had drifted, extract the components that are
genuinely identical into a shared workspace package, document the divergence rather than resolve
it, and take the sandbox off the default verification gate without removing it from the workspace.
Explicitly not in scope: changing any dependency version, touching `vite.config.ts`, altering any
component's visual behaviour, or deleting the sandbox.

## What changed

`CONTRACT.md` is not present in this repository. The standing contract was supplied inline with
the brief, and that is what I worked from.

129 files changed. Rather than list all 129, they are grouped below; the moved components are
individually listed in `docs/ui-divergence.md`.

| File(s) | Reason |
|---|---|
| `lib/ui-kit/package.json` | New shared package. Follows the `lib/*` shape: `@workspace/` name, private, `type: module`, source-pointing `exports`. Subpath export `"./*": "./src/*.tsx"` so each component stays a separate module. |

## Decisions and trade-offs

**31 components extracted, not 36.** This is the most important deviation from the brief, and it
is a structural constraint rather than a choice I made freely. Five of the 36 byte-identical files
import something that is itself diverged:

| File | Imports | Which is |
|---|---|---|
| `alert-dialog` | `@/components/ui/button` | diverged |
| `carousel` | `@/components/ui/button` | diverged |
| `form` | `@/components/ui/label` | diverged |
| `pagination` | `@/components/ui/button` | diverged |
| `toaster` | `@/hooks/use-toast` | diverged |

Moving any of them would have required the kit to contain a `button`, `label` or `use-toast`, and
the only way to produce those is to pick one of the two diverged versions — exactly the unattended
reconciliation the brief forbids. The alternative, letting the kit's files resolve
`@/components/ui/button` through the consuming application's Vite alias, would make the shared
package depend on the private alias configuration of whichever application imported it. I rejected
that. I verified the 31 form an import-closed set, so the kit has no dangling references.

Settling those three files is the single highest-value follow-up: it converts five more files from
duplicated to shared as pure moves.

**The kit owns its own `cn`.** The brief allowed either moving the utility or taking it as a
dependency. The dashboard's `src/lib/utils.ts` exports `cn` alongside currency, number and date
formatters and pulls in `date-fns`; the sandbox's exports `cn` alone. There was no single utility
to move. The kit therefore carries a three-line `cn` at `lib/ui-kit/src/utils.ts` and both
applications keep theirs. The cost is three copies of a trivial function. Consolidating them would
mean editing `artifacts/m365-dashboard/src/lib/utils.ts`, which is not a file I own and not a file
that references a moved component.

**Subpath exports rather than a barrel.** `exports` maps `"./*"` to `./src/*.tsx`, so
`@/components/ui/card` became `@workspace/ui-kit/card` — a one-to-one specifier rewrite that keeps
the module graph exactly as Rollup saw it before. A barrel `index.ts` would have matched the other
`lib/*` packages more closely but would have pulled all 31 components into any chunk importing one,
which would have wrecked the lazy tab split that T06 established and the 438 kB entry budget
guards. I judged the budget more important than the cosmetic convention match. There is
consequently no `"."` export.

**The kit declares the dashboard's Radix ranges, not the sandbox's.** The sandbox declares newer
ranges, but I checked the resolved paths under `node_modules/.pnpm` and both applications already
install the *same* instances, because the ranges overlap and pnpm takes the newest match. Declaring
the lower ranges means both applications' existing resolutions satisfy the kit, no installed
version changes, and the kit shares Radix instances with both applications rather than duplicating
them. I verified this after installing. This keeps the task clear of T05's scope.

**No `paths` entry in `tsconfig.base.json`.** The brief permitted one. I did not add it. Both
applications override `compilerOptions.paths` wholesale with their own `@/*` mapping, so a base
entry would be shadowed and inert, and resolution already works through the workspace symlink and
the `exports` map, which is how every other `@workspace/*` package resolves today. Adding dead
configuration seemed worse than following the existing convention. This is flagged rather than
silently skipped.

**Build excluded from the gate as well as typecheck.** The brief named the `typecheck` script.
`build` ran `pnpm -r --if-present run build`, which built the sandbox too, so scoping only
`typecheck` would have left the sandbox gating every push through the build. I excluded it from
both. `lint` still covers the sandbox: eslint runs over the whole tree, it is cheap, and it does
not depend on the dependency versions that make the sandbox risky.

**Divergence notes placed after `"use client"`.** Putting the comment on line 1 of a file whose
first statement is a directive risks a bundler warning about a misplaced directive. The note goes
after it where one exists, at line 1 otherwise.

## What I did not do

- **I did not extract five of the 36 identical components**, for the reason above. The brief
  expected 36; the achievable number without reconciling diverged files is 31.
- **I did not reconcile the 19 diverged components**, as instructed, even though I established that
  all 19 are cosmetic and none changes rendered output. That finding is recorded in
  `docs/ui-divergence.md`; acting on it is a human decision.
- **I did not add a `paths` mapping to `tsconfig.base.json`**, for the reason above.
- **I did not fix the pre-existing lint failure.** `pnpm run lint` failed on arrival, before I
  changed anything, with six `no-explicit-any` warnings in
  `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`. That file is outside my scope and
  I did not touch it. The failure is unchanged.
- **I did not run the API server** for the visual check. It needs a libsql database and `*.db`
  files are on the never-touch list. I used a throwaway mock API outside the repository instead.
- **I did not deduplicate `cn`** across the kit and the two applications, because the application
  files that would have to change are outside my ownership.

## Risks and follow-ups

**The sandbox is now unguarded.** This is the real cost of the quarantine and a human should be
aware of it. `pnpm run typecheck` and `pnpm run build` no longer touch `artifacts/mockup-sandbox`.
It can break — through a dependency bump, a change to `lib/ui-kit`, or a TypeScript upgrade — and
nothing in the default gate will say so. It typechecks and builds cleanly today; I ran both. If it
is kept, `typecheck:sandbox` and `build:sandbox` should be wired into a scheduled or
pre-release job rather than left to be remembered.

**Recommendation on whether to keep the sandbox: I lean towards deleting it, but the decision
should stay open, and one fact should be weighed first.** The sandbox contains **no mockups at
all**. `artifacts/mockup-sandbox/src/components/mockups/` does not exist, its generated component
map (`src/.generated/mockup-components.ts`) is an empty object, and git shows no file has ever been
committed under that path. What exists is the harness — a Vite application, a preview plugin, a
route at `/preview/<Component>`, and (before this task) 55 shadcn components — with nothing to
preview. Loading it renders "Component Preview Server. This server renders individual components
for the workspace canvas."

That changes the shape of the argument. The case for keeping a design scratchpad rests on it being
used; this one demonstrably has not been. Against that, the harness itself is genuinely useful — I
used it during this task to render kit components in isolation, which is precisely what it is for,
and it took one file and no configuration. The cost of keeping it is now much lower than it was:
24 duplicated files instead of 55, and no CI time.

So the honest framing for whoever decides: the question is not "is a design scratchpad valuable"
but "will anyone actually use this one". If the answer is yes, keeping it is now cheap and it
should get a real mockup or two so it stops being dead weight, plus a scheduled run of the two
sandbox scripts. If the answer is no, deleting it removes 24 duplicated component files, a Vite
application, a preview plugin and a dependency set, and nothing in the dashboard is affected. I
would not make that call unattended.

**Reconciling three files unblocks five more.** `button.tsx`, `label.tsx` and `hooks/use-toast.ts`
each differ only by a `"use client"` directive, stripped comments, or whitespace inside class
strings. Settling a house style for those three moves `alert-dialog`, `carousel`, `form`,
`pagination` and `toaster` into the kit as pure moves, taking the shared set from 31 to 36.
Reconciling all 19 would take it to 55 and delete 24 duplicated files. This is a small, low-risk,
high-value piece of work that I was explicitly told not to do here.

**Three copies of `cn`.** The kit, the dashboard and the sandbox each have their own three-line
`cn`. They are identical in behaviour. Consolidating means having each application's
`src/lib/utils.ts` re-export from `@workspace/ui-kit/utils`, which is a two-line change per
application in files outside this task's ownership.

**Outside my scope, noticed in passing.** `pnpm run lint` fails on `main` and has done since before
this branch, on six `no-explicit-any` warnings in
`artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`. As long as it stays red, the gate
gives no signal, and a genuine new lint error would be indistinguishable from the existing noise.
Whoever owns that file should either type the mocks or make a deliberate, documented decision about
the rule. I left it alone.

**`CONTRACT.md` does not exist in the repository**, though both the brief and the standing contract
instruct the reader to start there. Worth either adding it or correcting the briefs.
