# T02: Route and store test coverage

## 1. Objective

The api-server suite was 101 tests of pure logic. No HTTP route had ever been served, no SQLite
store had ever been driven against a real client, and three of the eight findings rule groups
(security, compliance and licensing) had no tests at all. The job was to close the two gaps that
matter most — the store logic that can produce a plausible-looking but wrong findings register,
and the route layer that had never been exercised end to end — to write the missing rule groups,
and to add a meta-test that makes the rule gap impossible to reopen quietly. Coverage reporting
was to be added and measured, but no threshold set: that is a human's call once the achieved
figure is visible.

## 3. Decisions and trade-offs

**1. Editing `artifacts/api-server/package.json`, which is not on my owned-files list.**
Step 4 of the brief says to add `@vitest/coverage-v8`. That cannot be done without touching the
package manifest and the lockfile. I judged the explicit instruction to win over the file list,
because the file list exists to prevent collisions and a one-line additive `devDependencies`
entry is the smallest possible change. Flagged here so a reviewer can see it deliberately rather
than discover it. Nothing else in that file was touched.

**2. Redirecting `createClient` rather than pointing `METRIC_DB_PATH` at `:memory:`.**
The brief asks for an in-memory store, but `metricStore.getDbPath` runs the environment override
through `path.resolve` and hands the result to `createClient` as a `file:` URL, so `:memory:`
resolves to a nonsense Windows path. The two existing store test files work around this with a
scratch `.db` file in `os.tmpdir()`. Rather than copy that, the fixture mocks `@libsql/client`
so `createClient` always opens `:memory:`. The gain is that every line of `metricStore`,
`findings/store` and `scanStore` runs unmodified against a genuine libSQL client, including the
transaction semantics the atomicity test depends on, with no file ever created. The cost is one
more module boundary being mocked, and the fixture has to hand its module instances back to the
caller — a test that statically imports a store directly gets a different, unmocked instance.
That constraint is documented in the fixture's doc comment.

**3. `vi.resetModules()` and a fresh module graph per test, rather than truncating tables.**
`findings/store.ts` holds two pieces of module state that matter to the behaviour under test:
the single-flight guard and `lastRegenSnapshotSignature`. Truncating tables between tests would
leave both in place and make the signature-gating tests depend on execution order. A fresh graph
per test costs roughly 450 ms per route test (re-importing express and the whole router), which
is why the suite went from 9.6 s to 17.4 s. I took the wall-clock cost for the isolation.

**4. Stubbing Graph at `fetchGraphJson`, not at `fetch`.**
`fetchGraphJson` in `collectionIssues.ts` is the single seam every collector and the onboarding
permission check go through, and it is where the retry, timeout and issue-classification logic
ends. Stubbing there keeps the route, validation and serialisation path production-real while
giving tests a typed reply to stage. Stubbing `fetch` would have dragged the token acquisition
and `@azure/identity` into every test for no gain.

**5. Forcing the atomicity failure with a schema violation rather than a mock.**
`regenerateFindings` builds its statements and hands them to `client.batch(..., "write")` in one
go, so there is no injectable seam part-way through. Returning a finding with a null `title`
makes the insert violate the `NOT NULL` constraint, which fails the batch after at least one
good statement has been staged. That is a real part-way failure through the real code path.
Proof that it catches an actual regression is in section 5.

**6. Asserting the PDF body by decompressing it.**
The brief asks for "a non-trivial number of bytes". The executive PDF is about 1.7 kB for three
findings and about 1.5 kB for none, so a byte count alone cannot tell a real report from a blank
one served as a success. pdf-lib flate-compresses its content streams and writes strings as hex
literals, so the test inflates the streams and decodes the literals before asserting that the
findings actually reached the page. The byte-count assertion is kept as well. As a side note,
the existing `executivePdf.test.ts` assertion `expect(bytes.toString("latin1")).not.toMatch(...)`
passes trivially for this reason — it is asserting against compressed bytes. I did not change it
(not my file); it is in section 6.

**7. Encoding "as designed" for onboarding gating as: the API does not gate.**
`needsOnboarding` is computed and returned by `/api/onboarding/status`, and nothing in the API
acts on it — data routes serve an ungated request while onboarding is incomplete. That is
coherent given the API is unauthenticated and loopback-bound by default, so gating here would
add no protection. The test states this explicitly with the reasoning in a comment, so that
changing either half of the arrangement is a deliberate act rather than an accident.

**8. Recording tested rule ids in-process rather than parsing the test file.**
The meta-test needs to know which rules have tests. The `rule()` helper the file already used to
look a rule up now also records the id, and the meta-test compares that set against the engine's
`registeredRules` export. This means a rule only counts as tested if a test actually executed
against it — a `describe.skip` or a deleted assertion drops it out of the set. The trade-off is
that all rule tests must live in one file, because vitest gives each file its own module
instance and therefore its own registry. That file is now 519 lines. I judged the alternative
(a second file whose coverage the meta-test cannot see) to be worse.

## 6. Risks and follow-ups

**Recommended coverage threshold.** Set `lines: 40`, `branches: 78`, `functions: 55`,
`statements: 40`. The achieved figures are 45.07 / 82.07 / 64.63 / 45.07. The margin is
deliberate and asymmetric. The largest single block of uncovered code is `src/lib/collectors/`
(nineteen files, 12.75% lines), and whoever tackles it will move the aggregate a long way; a
floor set at the achieved figure would break the build for anyone who legitimately adds a large
untested collector while working on something else. Branches are the number worth defending
hardest — 82% branch coverage means most of the conditional logic that decides what a finding
says is now exercised, and a regression there is exactly the failure mode this product cannot
afford. I would raise the floor to the achieved figure once the collectors have their own
tests, and not before. Thresholds belong in `artifacts/api-server/vitest.config.ts`, where the
place for them is already marked with a comment.

**The lint gate is red on `main`.** Six `no-explicit-any` warnings in `emailAuthDns.test.ts`
against `--max-warnings 0`. Every agent in this programme will hit it. It wants one commit from
someone who owns that file.

**`artifacts/api-server/coverage/` is not git-ignored.** `.gitignore` has `/coverage`, which is
anchored to the repository root and does not match the per-package directory the CI step and
this config both write to. It shows up as untracked after any coverage run and will eventually
be committed by accident. `.gitignore` is outside my scope; the fix is to change `/coverage` to
`coverage/`.

**`computeDrift` classifies a newly-passing control as both resolved and changed.** A finding
that moves from `fail` to `pass` appears in `drift.resolved` (correctly) and also in
`drift.changed`, because its `check_status` differs from the previous scan. The three lists are
not a partition. The dashboard shows them side by side, so today this reads as double-counting
rather than as a wrong answer. The test asserts the current behaviour with a comment explaining
it; if the intent is a partition, the rule needs to skip `changed` when the transition is to
`pass`. Worth a product decision.

**A malformed JSON request body returns 500, not 400.** `express.json()` raises a `SyntaxError`
carrying `status: 400`, but `errorHandler` ignores the status and answers 500 for everything.
The response is safe — no stack, no path, fixed message, which is what the test asserts — but a
client that sends bad JSON is told the server broke. Honouring `err.status` when it is a 4xx
would be a small, contained improvement. Out of scope here: `errorHandler.ts` is a non-test
source file.

**The metric TTL is one second shorter than it looks.** `expires_at` is written as
`floor(now) + ttl` and read as `expires_at > floor(now)`, so a 60-second TTL is fresh for
seconds 0 to 59 and stale from second 60. Harmless at the 3600-second production TTL, and the
test pins the boundary explicitly, but worth knowing before anyone writes a short-TTL cache
against this store.

**`executivePdf.test.ts` asserts against compressed bytes.** Its
`expect(bytes.toString("latin1")).not.toMatch(/Zo\? M\?ller/)` cannot fail, because pdf-lib
flate-compresses the content stream — the string is not in the raw bytes either way. It is a
passing test that checks nothing. The stream-inflating helper in
`m365Export.route.test.ts` shows how to assert it properly. Not my file, so left alone.

**`src/lib/export/excel.ts` is at 2.53% line coverage** and is now the largest untested block
outside the collectors. Two export routes serve it.

**Suite duration is up from 9.6 s to 17.4 s.** The cause is `vi.resetModules()` plus a fresh app
import per route test, at roughly 450 ms each. If this becomes a problem, the route tests could
share one fixture per file and truncate tables between tests, at the cost of the module-state
isolation described in decision 3.

section 5, which involved five full suite runs (baseline coverage, final coverage, the
no-network run, and two break-and-restore cycles).

Token cost: not instrumented in this environment, so no figure is available.
