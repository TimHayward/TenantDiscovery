## 1. Objective

`main` was failing CI at the lint step (11 errors, 33 warnings). The job was to clear every one
of those findings properly — not by disabling rules or narrowing checks — and then raise the
lint gate so it fails on any future warning instead of letting them accumulate silently. On top
of the lint cleanup, the brief asked for the `engines` field to be pinned across the workspace,
a `.gitignore` gap around local metrics databases to be closed, and a coverage step to be added
to CI, all so that the other eleven agent tasks in this programme have a lint/build/test signal
they can trust rather than one they each have to individually decide whether to fix.

## 3. Decisions and trade-offs

**The four empty-catch blocks.** All four (three in `CollapsibleSection.tsx`, one in
`SecurityTab.tsx`) wrap `localStorage.getItem`/`setItem`/`removeItem` calls used to persist
which dashboard sections are expanded or collapsed. `localStorage` can throw in private
browsing, when the browser has disabled web storage, or when quota is exceeded — none of which
is under this code's control, and the value being persisted is a non-critical UI preference (if
the write fails, the section just falls back to its default open/closed state next load). Logging
these through the existing logger would mean logging routine, expected browser behaviour on every
affected page load in Safari private mode, which is noise, not signal. I added a one-line comment
inside each block explaining this instead of leaving it silently empty, which satisfies
`no-empty` honestly. Before making this call I checked whether any of the four functions returned
or depended on the outcome of the `localStorage` call in a way that would make silent failure
wrong — none do; each caller already has a sensible fallback (`defaultOpen`, or "section keeps
its current state").

**The `react-hooks/exhaustive-deps` fixes.** There were two distinct underlying causes, and I
treated them differently:
- `SecurityTab`'s `controls` and `AppsTab`'s `apps` were both `x = data?.field ?? []` computed
  directly in the component body (not inside a `useMemo`), which means each one is a *new array
  reference* on every render even when `data` hasn't changed. ESLint's suggested "logical
  expression" fix — hoist the whole expression into its own `useMemo` keyed on the underlying
  query data — is what I did in both cases. I read the components end-to-end to confirm nothing
  else relied on the old per-render array identity for a reason (e.g. no code compared array
  references directly, only read values off them), so switching to a memoized array changes
  nothing observable, only how often downstream `useMemo`s actually recompute.
- `UsersTab`'s `getChecklistMeta` was a plain closure defined fresh every render and called
  inside `section1Groups`' `useMemo` without being listed as a dependency. Blindly adding it to
  the dependency array (the "mechanical fix") would have made `section1Groups` recompute on
  every render regardless of whether anything it actually depends on changed — a real perf
  regression, since `section1Groups` builds a fairly large checklist array. Instead I traced what
  `getChecklistMeta` actually reads (`CHECKLIST_FIELD_MAP`, a static object, and `fieldMetadata`,
  which is already its own `useMemo` keyed on `usersWithMetadata`) and wrapped `getChecklistMeta`
  in `useCallback` keyed on `fieldMetadata` alone, after hoisting the static `CHECKLIST_FIELD_MAP`
  out of the component so it isn't itself a fresh reference each render. This makes
  `getChecklistMeta` stable exactly as often as its real dependency changes, so listing it in
  `section1Groups`' dependency array reproduces the original recomputation frequency rather than
  making it worse. ESLint then correctly flagged the pre-existing `fieldMetadata` entry in that
  same array as redundant (since it's now only reached indirectly through `getChecklistMeta`),
  which I removed.

**The four `any`s in `SecurityTab.tsx`.** The brief suggested typing them from the generated
`@workspace/api-zod` package. On inspection, all four `any`s are recharts render-callback prop
shapes (a custom `<Tooltip content={...}>` component, a `<Pie label={...}>` renderer, and a
`<Tooltip formatter={...}>` callback) — library callback signatures, not API response shapes.
`@workspace/api-zod` wouldn't have produced a meaningful type for any of them. I used recharts'
own exported `TooltipProps<TValue, TName>` and `PieLabelRenderProps` types instead (with
`TValue=number, TName=string`, matching what's actually passed), which is the real type source
for this code. This is a deviation from the brief's literal suggestion, made because the
suggestion didn't match what the code actually needed; I judged "real types drawn from a
generated source" as the operative instruction and applied it to the correct source.

**File-ownership interpretation for `engines`/README.** The brief's file-ownership list names
only the root `package.json`, but the Work section explicitly instructs adding `engines` to "the
root package.json and both application packages" and updating "the README's prerequisites line."
I read this as the Work section refining the abbreviated ownership list for this one instruction,
rather than a contradiction, and touched `artifacts/api-server/package.json`,
`artifacts/m365-dashboard/package.json`, and `README.md` — but strictly for the `engines` field
and the one prerequisites line, nothing else in those files.

**Commit granularity.** I grouped related fixes per commit (e.g. all of `SecurityTab.tsx`'s
`any`/no-empty/exhaustive-deps fixes landed together, since they're all in one file) rather than
one commit per individual lint finding, which would have produced ~40 commits with little
individual value. Each commit is independently buildable and its message explains the specific
findings it addresses.

## 4. What I did not do

- **`vitest run --coverage` will not pass yet.** It needs `@vitest/coverage-v8` installed as a
  devDependency, and the brief scopes "any package.json dependency block" to T05, explicitly out
  of scope for this task. I added the CI step exactly as specified (text + lcov reporters,
  uploaded as an artifact, no threshold) and verified locally that the CLI wiring itself is
  correct — running `vitest run --coverage` fails with `MISSING DEPENDENCY: @vitest/coverage-v8`,
  not an argument-parsing error — so the step will start working the moment that dependency is
  added by whoever owns that package.json block. This is flagged again under Risks below because
  it directly affects the "gate is green" claim this task exists to deliver.
- **`pnpm run lint` (with the new `--max-warnings 0`) does not currently pass**, for the same
  boundary reason in reverse: `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`
  carries six `@typescript-eslint/no-explicit-any` warnings, and the brief places every
  `__tests__` directory out of scope for T01 (T02 owns those). I left that file untouched. Every
  warning in every file this task owns is cleared — `pnpm exec eslint .` restricted to non-test
  scope produces zero output — but the workspace-wide `pnpm run lint` will stay red until T02's
  branch lands. I did not weaken the new `--max-warnings 0` gate (e.g. with a per-file override)
  to paper over this, since that would be exactly the kind of "weaken a check to make it pass"
  the standing contract prohibits.
- I did not investigate or fix the apparent dead `guestAccessEnabled` in `TeamsSharePointTab.tsx`
  beyond removing the unused local — see Risks below.
- I did not add a `pnpm run build` step to CI; the brief didn't ask for one and I didn't want to
  change CI's shape beyond what was specified.

## 6. Risks and follow-ups

- **The raised gate will not go fully green from this branch alone.** `pnpm run lint` needs
  T02's `__tests__` cleanup merged; the new CI coverage step needs T05 (or whoever owns
  dependency blocks) to add `@vitest/coverage-v8`. Both are called out above and are inherent to
  how the work was split across this wave, not defects in this task's output — but whoever merges
  this branch should be aware the gate won't show fully green until those two land too.
- **`TeamsSharePointTab.tsx`'s `guestAccessEnabled` looks like a real bug, not just dead code.**
  It's computed from `teamsData?.guestAccessEnabled` and then never read anywhere — no checklist
  item or badge references it, even though the equivalent `externalAccessEnabled` local is wired
  into a checklist row at line 357. This looks like a guest-sharing checklist item was either
  removed or never finished. I only deleted the now-provably-dead local (in scope for this lint
  task); I did not investigate or restore the intended behaviour, since that's a feature-logic
  change outside a lint-cleanup task's scope. Worth a look by whoever owns that tab.
- **`artifacts/api-server` builds to a single 4.8 MB `dist/index.mjs`** (esbuild prints this as a
  size warning, not an error). Pre-existing, unrelated to this task, not touched.
- **CONTRACT.md does not exist in this repository.** The task brief said to read it first; I
  used the standing-contract text provided in my dispatch instructions instead, per its own
  statement that it applies to all of T01–T12 and wins in any conflict. Worth confirming whether
  a `CONTRACT.md` was meant to be committed to the repo, since every subsequent task's brief
  presumably makes the same reference.
