# T08: Per-host concurrency limiting for collection

## 1. Objective

The collectors already coped with being throttled: `fetchResourceWithRetry` retried a 429 with
bounded, jittered backoff and honoured `Retry-After`. Nothing stopped them causing the throttling
in the first place. A background refresh fans out nineteen collection tasks, and several of those
issue one request per discovered principal or device, so on a tenant with a few thousand
principals the tool opens a few thousand concurrent Graph requests, all of which are throttled and
all of which then retry. The job was to put a ceiling on concurrent requests per host, wired into
the shared fetch helper rather than at each call site; to stop capping a server-provided
`Retry-After` at thirty seconds; to finish moving the last collectors that bypassed the shared
helpers onto them; and, while in `security.ts`, to replace the `Math.random()` device-key fallback
that made drift report the whole non-Entra estate as churn on every run. This is backlog 6.2, the
remainder of 5.1, and 5.9.

## 3. Decisions and trade-offs

**Why 8, and what would change it.** Eight is a judgement, not a measurement, and I want to be
plain about that. The reasoning: Microsoft documents Graph throttling as a per-app, per-tenant
budget rather than a fixed concurrency limit, so there is no published number to copy. What the
limiter has to achieve is that the steady-state request rate stays under whatever the tenant
tolerates while the nineteen collection tasks still overlap rather than serialise. At 8 concurrent
requests per host and a typical Graph latency of 100-300ms, the tool sustains roughly 25-80
requests per second against Graph, which is in the range a single app registration handles without
429s in practice, and it keeps enough parallelism that a refresh does not become nineteen
sequential collections. It is also low enough to be safe on a small tenant, where the cost of
being conservative is a few seconds.

The evidence that would change it is a measured one, and it is measurable today: run a refresh
against a real tenant with `GRAPH_MAX_CONCURRENCY` set to 8, 16 and 32, and record the number of
429s in the collection issues alongside the wall-clock duration. If 16 produces no more 429s than
8 and is materially faster, the default is too low. If 8 still produces 429s on a large tenant,
it is too high and the right response is to lower it rather than to lean harder on retry. A
second, weaker signal would be Graph's `RateLimit-Remaining` response headers, which the fetch
helper does not currently read; recording those per host would let the limiter adapt instead of
being configured, which is the proper long-term answer and is out of scope here.

**The permit is held across the `Retry-After` wait.** The alternative is to release it during the
sleep and re-acquire afterwards. I chose to hold it. A host that has asked to be left alone should
see fewer concurrent requests while it recovers, not the same number, and releasing the permit
would let a queued request start the moment a throttled one begins waiting, which is exactly the
behaviour the limiter exists to prevent. What this gives up is throughput: a 120-second
`Retry-After` now occupies one of eight slots for two minutes. That cost is bounded by the budget
being per host, so a throttled Graph cannot hold up Defender collection, and by there being at
most `GRAPH_MAX_RETRIES` such waits per request.

**Where the limiter is wired.** Inside `fetchResourceWithRetry`, which is the single function every
helper funnels through. Putting it at the call sites would have been marginally more flexible and
would have let a collector opt out of the ceiling for a genuinely cheap request, but the next
collector someone writes would forget it. The verification found three call sites that still issue
`fetch` directly and therefore escape the limiter; see section 4.

**Raising the `Retry-After` ceiling to 120s but not the computed backoff.** A server-provided value
is an instruction and is honoured up to two minutes. The computed backoff is our own guess, and
keeping its lower cap means a transient 5xx with no header still recovers quickly. I deliberately
did not add jitter to the server-provided value: jitter exists to de-synchronise clients that
computed the same delay independently, whereas a `Retry-After` is the server's own number, and
adding noise to it would mean either waiting longer than asked or retrying early.

**A ceiling of zero is clamped to one, not treated as "unlimited".** Reading `0` as "no limit" is
the more common convention, but here it would mean a typo in an environment file silently removes
the protection this task exists to add. Clamping to 1 makes the mistake slow and obvious rather
than invisible.

**Unknown hosts get the default and no override.** `api.powerbi.com` and any future host get a
budget of 8 with no environment variable. Adding a generic `MAX_CONCURRENCY` fallback variable
would have been easy, but every host the collectors reach today is one of the three named ones
plus Power BI, and an unrecognised host is more likely to be a mistake than something worth tuning.

**Defender keeps its scope-alias probe.** The brief asked for a variant parameterised on base URL
and scope rather than special-casing, and that is what `fetchResourceJson` and
`fetchAllResourcePages` are. The one thing I left in `security.ts` is the probe that discovers
which of the two Defender scope aliases a given tenant will issue a token for, because that is a
genuine property of Defender rather than of fetching, and pushing it into the shared helper would
have made the helper know about Defender.

**The Defender migration preserves "discard partial data on failure".** The old loop returned an
empty machine list when any page failed. The shared helper returns what it collected before the
failure, which is more useful. I kept the old behaviour, because changing what the device
inventory contains is a separate decision from moving the collector onto the shared helper, and
bundling it would make this diff harder to review. It is listed as a follow-up.

**The device-key tuple.** For Intune the fallback hashes device name, operating system and
enrolment date, which required adding `enrolledDateTime` to the `$select` (it was already on the
`GraphManagedDevice` type, so no file outside my scope was touched). For Defender there is no
enrolment date on the selected fields, so the tuple is name and OS platform. I deliberately left
`osVersion` and `lastSyncDateTime`/`lastSeen` out of both tuples: they change when a machine is
patched or simply checks in, which would reintroduce the churn this is fixing, just less often and
therefore more confusingly. The name is required as an anchor, so a key is never derived from an
operating system alone, which would collide across unrelated devices.

**Devices with nothing stable are excluded and noted, not keyed.** The brief allowed either. A
device with no Entra device id, no source id and no name has nothing that survives to the next
collection, so any key is invented and will report churn forever. `collectSecurityEstate` now
returns a `collectionIssues` array carrying that note. This is an additive field; I checked before
adding it that `DefenderTab.tsx` already calls `getCollectionIssues(data)` on the estate payload
and renders the result, so the field lights up an existing UI path rather than needing one. I did
not add `partialData`/`permissionError` alongside it, because unlike `collectionIssues` those are
not read for this payload and would be speculative.

**`deviceSummary.mde` still counts raw Defender machines**, including any that were excluded from
the inventory. That figure answers "how many machines does Defender know about", which is true
regardless of whether we could key them, and the excluded count is reported separately as a note.

**Test placement.** The device-key and collector-issue cases are really `security.ts` tests, but
the brief's owned file list contains no collector test file, and creating one would have been a
scope breach. They live in `collectionIssues.test.ts`, which I do own and whose subject matter
(collection issues, and the helpers the collectors were migrated onto) covers them. A reviewer may
reasonably want them moved.

**`licenses.ts` needed no work.** The brief states it "still uses the Graph SDK client directly

**`backgroundRefresh.ts` needed no work.** I considered adding a ceiling on concurrent *tasks*

benchmark shows `triggerAll` peaking at 8 per host with all nineteen tasks running, which is the
outcome a task ceiling would have been trying to achieve.

**No adaptive limiting.** The limiter is a fixed ceiling. Reading Graph's `RateLimit-*` response
headers and adjusting the budget would be strictly better and is noted as a follow-up.

**Lint does not pass, and I did not make it pass.** See section 5.

### 1. A hundred requests never exceed the ceiling, asserted on the maximum observed

`concurrency.test.ts` records the greatest number of request bodies running at once, not the final
count, because a limiter that did nothing would pass the latter. The assertion is `toBe(8)` rather
than `toBeLessThanOrEqual(8)`, so it also proves the host stays busy:

```
✓ the configured ceiling > holds a hundred concurrent requests to the observed maximum of eight
✓ the configured ceiling > defaults to eight when nothing is configured
✓ the configured ceiling > gives each host its own budget
```

### 2. A rejected request releases its permit

Twenty requests of which every other throws. The batch settles with 10 rejected and 10 fulfilled,
all 20 bodies having run, and a peak of 4 in flight. A second case then fans out twelve
all-rejecting requests and afterwards proves four fresh requests can still overlap, which would be
impossible if any permit had leaked:

```
✓ permit accounting > releases the permit of a rejected request, so the batch still completes
✓ permit accounting > returns every permit after a batch of rejections, not merely enough to make progress
✓ permit accounting > propagates the rejection rather than swallowing it
```

### 7. Full background refresh against a stubbed Graph, timed

A throwaway harness ran `triggerAll` with all nineteen tasks, `metricStore`/`scanStore` stubbed and
`fetch` replaced by a model server: 10ms latency per request, and `adminExposure` given 800 unknown
principals so its per-principal fan-out is real. Two server models, each run with the ceiling
effectively disabled (100000) and set to 8. The harness is not committed; it is reproduced as a
follow-up suggestion below.

| Server model | Configuration | Wall clock | Requests | Throttled (429) | Peak in flight (Graph) | Collection issues |
|---|---|---|---|---|---|---|
| Generous (never throttles) | before, no ceiling | **145ms** | 880 | 0 | 810 | 0 |
| Generous (never throttles) | after, ceiling 8 | **1,792ms** | 880 | 0 | 9 | 0 |
| Throttling above 10 concurrent | before, no ceiling | **5,190ms** | 3,392 | 3,307 | 803 | 788 |
| Throttling above 10 concurrent | after, ceiling 8 | **1,906ms** | 881 | 2 | 9 | 0 |

**The limiter is materially slower against a server that never throttles: 145ms to 1,792ms, about
twelve times.** That is the honest worst case and I am not going to bury it. It is also not a
server that exists: it accepted 810 simultaneous requests from one app registration with no
penalty.

Against a server that throttles, which is what Microsoft Graph does, the limiter is **2.7 times
faster** (5,190ms to 1,906ms), issues **a quarter of the requests** (881 against 3,392, because
3,307 of the old run's requests were retries of throttled ones), and **produces complete data
instead of 788 collection issues**. The 788 is the failure mode from the brief reproduced exactly:
not an error, a refresh that takes far longer and comes back partial.

The trade is therefore peak throughput against an idealised server, in exchange for correctness and
speed against a real one. The crossover is where the tenant's tolerance sits: if a tenant genuinely
accepted 800 concurrent requests, the ceiling would be pure cost, which is precisely why it is
configurable and why section 3 sets out what evidence would move the default.

Two details worth reading off the table. First, "peak in flight (Graph)" is **9**, not 8: that is
the `intune.ts` direct `fetch` documented in section 4, and it is the measurement that found it.
Second, the totals include `api.powerbi.com` (peak 2) and `api.security.microsoft.com` (peak 1) on
their own budgets, which is the per-host separation working.

## 6. Risks and follow-ups

1. **The ceiling is not airtight.** `collectors/intune.ts:234` issues a Graph `POST` with a direct
   `fetch` and escapes the Graph budget; `exchangeOnline.ts:64` and `dns/emailAuthDns.ts:67` do the
   same on their own hosts. All three are outside my owned files. Moving the intune one onto
   `fetchGraphJson` needs a `POST` body parameter on the helper, which the helper does not have
   today. The Exchange Online one is the more concerning of the other two, because it is a
   per-mailbox call shape. **Recommended: a small follow-up task that adds request-body support to
   the shared helper and migrates all three.**
2. **If a user sets the limiter to 1.** The brief asked me to state this. Collection against that
   host becomes fully serial. Nothing breaks, no data is lost and no request fails; a refresh
   simply takes as long as the sum of its requests. On the 800-principal model above that is the
   difference between roughly two seconds and roughly thirty; on a real tenant with several thousand
   principals and 200ms Graph latency it is the difference between a refresh of a few minutes and
   one of ten to twenty. The dashboard shows stale data for that whole period rather than an error,
   which makes the cause hard to spot. This is why `README.md` and `.env.example` both say plainly
   that 1 serialises collection and will make a refresh take considerably longer, and why 0 clamps
   to 1 rather than being read as "unlimited". A follow-up worth considering is a startup log line
   at warn level when either ceiling is configured below 4.
3. **The refresh benchmark should become a permanent artefact.** The harness that produced section
   5's table is throwaway because no committed file in my owned list was an appropriate home for it.
   It is about eighty lines and it is the only thing in the repository that can answer "did that
   change make collection slower". Worth landing under its own task, with a home in
   `src/lib/__tests__/` and a modest assertion so it does not rot.
4. **Adaptive limiting beats a fixed ceiling.** Graph returns `RateLimit-Limit`,
   `RateLimit-Remaining` and `RateLimit-Reset` headers that the fetch helper ignores. Reading them
   and adjusting the per-host budget would remove the need to guess a default at all. This is the
   proper answer to "why 8" and is a larger piece of work than this task.
5. **Defender partial data is still discarded on failure.** If page seven of the Defender machine
   list fails, the first six pages are thrown away and the estate reports zero machines with an
   error. The shared helper now returns those pages; `security.ts` explicitly drops them to preserve
   existing behaviour. Someone should decide whether partial device inventory is better than none,
   and if so it is a one-line change.
6. **The Defender fallback tuple is weaker than the Intune one.** Intune keys on name, OS and
   enrolment date; Defender keys on name and OS platform only, because no stable date is available
   on the selected fields. Two Defender machines with the same DNS name and platform will collide.
   `MdeMachine` in `collectors/graphTypes.ts` (not in my scope) would need a `firstSeen` field added
   and selected to fix this properly.
7. **`mdeStatus.status` is now 200 on success rather than the literal last page status.** The shared
   helper only surfaces a status when a page fails. Every non-failing page was 2xx by definition, so
   this is a distinction without a difference in practice, but it is a behavioural detail a reviewer
   should see rather than discover.
8. **The estate's new `collectionIssues` field will start showing issues in the UI that were
   previously invisible.** `DefenderTab.tsx` already renders `getCollectionIssues(data)` on that
   payload and has been receiving an empty array. Graph page failures on devices, managed devices,
   service principals and OAuth grants were silently dropped before and are now reported. This is
   the correct behaviour, but it will look like a regression to anyone who sees a new warning banner
   on a tenant whose collection was always partial.
9. **The security posture was not touched.** No change to the loopback binding, `ALLOW_REMOTE`,
   `assertSafeBinding`, helmet, CORS, SQL parameterisation, the DNS-over-HTTPS resolver or
   `minimumReleaseAge`. The limiter adds no dependency; it is about forty lines of standard library.
