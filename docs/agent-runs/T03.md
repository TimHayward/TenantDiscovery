# T03: Repository weight and data-exposure audit

## 1. Objective

Produce a decision-ready assessment of what the public `TenantDiscovery` repository is
carrying that it probably should not — large committed binaries, stale documentation, and
missing governance files — without making any of those judgement calls myself and without
touching anything but documentation. The core deliverable is
`docs/audits/repository-weight-and-exposure.md`: an inventory of every file over 100 KB in the
full git history (not just the working tree), an exposure assessment for each large asset
phrased as a yes/no question a human can answer, a verified fact-check of `replit.md` against
the current code, a governance-file gap analysis with a draft `SECURITY.md`, and two fully
written-out (but unexecuted) remediation paths — a history rewrite and a reversible tip-only
removal — with a recommendation on which to run and when.

## 3. Decisions and trade-offs

**Grouped the >100 KB inventory by path with churn summarised, rather than listing all 41 raw
blob objects.** The brief asks for "every committed file over 100 KB" from full history. A
literal blob-by-blob table would include nine historical versions of `pnpm-lock.yaml`, ten of a
generated manifest, and similar churn from ordinary source control — real pack weight, but not
an exposure question and not decision-relevant. I split the table: five rows for the
exposure-relevant assets (`attached_assets/*`, `.canvas/*`) with full path/size/type/commit/date
per the brief's exact ask, and a second, summarised table for the five churn-driven paths
(version count, current size, first-large commit) with a note that they're ordinary weight, not
addressed further. Traded off literal completeness of the raw table for a document a human can
actually act on — which is what the brief's own "decision-shaped, readable on a phone" framing
asks for.

**Used `file` (container metadata only) to establish type, not asked whether that crosses the
"do not inspect the interior" line.** The brief permits reporting by "name, size, type" — `file`
reports PDF page count, PNG dimensions, and Excel container format from headers, not document
content. I judged this squarely inside "type" and outside "inspect the interior," and verified
after the fact that no page text, cell value, or pixel content appears anywhere in my commits
(`git log -p` search below). I did not, at any point, open the PDF, XLSX, PNGs, or the three
`Pasted-*.txt` files in a viewer or text reader.

**Recommended correcting `replit.md` rather than deleting it.** The brief asks me to propose one
or the other, given the project is no longer meaningfully Replit-hosted. I chose correction
because the repository has no other architecture-orientation document — no `CLAUDE.md`, no
`ARCHITECTURE.md`. Deleting it removes the only thing of its kind; correcting it fixes the
actual defect, which is staleness. I flagged that renaming it away from "replit.md" is a
separate, larger decision I did not make.

**Did not recommend running the history rewrite now.** The brief asks me to prepare it, state
which option I'd choose, and stop — not to decide the exposure question, which I'm explicitly
told isn't mine to make. I recommended running the reversible, no-coordination tip-only removal
immediately for the pieces that are dead weight under any answer (the `Pasted-*.txt` files, the
`.canvas` duplicate), and holding the irreversible rewrite until a human confirms whether the
"Example M365 Tenant Assessment Report" is synthetic. The trade-off stated in the audit: if the
data turns out to be real, this means running remediation twice (tip removal now, history
rewrite later) rather than once — I judged that a smaller cost than either leaking real tenant
data during a longer decision window, or running an irreversible operation before the underlying
fact is known.

**Named the four other checked-out branches (`main`, `agent/t01`, `agent/t02`) as concretely
affected by a history rewrite.** I have visibility into `git worktree list` and `git branch -a`
from this environment. Since the multi-agent programme (T01–T12) runs each task on its own
branch against a shared `.git`, a `main` rewrite breaks every one of those branches' merge base
simultaneously. I judged this a fact about blast radius worth stating plainly in the remediation
section rather than a generic "notify collaborators," since it's specific and verifiable, not
guessed.

## 4. What I did not do

**Did not verify GitHub's public/private status directly.** I confirmed the remote URL
(`https://github.com/TimHayward/TenantDiscovery.git`) via `git remote -v` and took the brief's
statement that the repository is public as given, since I have no tool access to query GitHub's
API for repository visibility from this environment and the brief states it as an established
fact, not something to verify.

**Did not diff the two near-identical `Pasted-*.txt` files against each other.** The audit notes
their filenames and epoch suffixes are ten seconds apart and speculates they may be two versions
of the same paste, but I deliberately did not run `diff` on them, because that would mean reading
their content — outside my brief.

**Did not resolve the `replit.md` Node-version discrepancy as one of the four scored claims.**
I found it while verifying the four the brief named (it says Node 24; every `package.json`
declares `>=22`) and reported it as a bonus finding, since the brief was specific about which
four claims to check and I didn't want to overstate scope by scoring a fifth as if it were asked
for.

**Did not touch the pre-existing lint failure.** `pnpm run lint` fails identically before and
after my changes (six `@typescript-eslint/no-explicit-any` warnings in
`artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`, a file I don't own and didn't
touch). Noted per the standing contract's instruction to work around, not fix, a pre-existing
gate failure when the task is not T01.

## 6. Risks and follow-ups

Everything substantive is in the audit document's own findings (§2–§6 there). Summarised for a
reviewer who wants the short version without opening it:

- The exposure question on the "Example M365 Tenant Assessment Report" pair is unresolved and
  is the single highest-priority open item from this task — it blocks a clean answer on whether
  any remediation beyond tip-only removal is needed.
- `SECURITY.md` is the governance file to write first, given the product authenticates to
  Microsoft Graph with tenant-wide application permissions; a draft is in the audit document,
  proposal only.
- `attached_assets/` is missing from `.dockerignore` (unlike `.canvas/`, which is present),
  so every Docker build currently ships the full 7.49 MB into the build context regardless of
  the exposure decision. One-line fix, independent of everything else in this audit, left for
  whoever owns `.dockerignore`.
- If a history rewrite is ever chosen, every currently-open agent branch (`agent/t01` through
  whatever the programme reaches, plus `main` itself) needs to be accounted for beforehand — the
  audit document names the four worktrees visible from this environment as a concrete, not
  hypothetical, blast radius.
- `lib/db` (the `@workspace/db` package: drizzle-orm, drizzle-zod, libSQL) is a workspace member
  that nothing outside itself imports — noted in passing while fact-checking `replit.md`'s
  database claim, but out of scope to act on here since it's a source-tree question, not a
  documentation one.
