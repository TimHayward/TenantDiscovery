# T10: Offline demonstration mode with fixture tenants

## Objective

Make the whole dashboard runnable from a recorded snapshot instead of a live
Microsoft Graph connection, so that the product can be shown, developed against
and tested without a tenant, an app registration, consented permissions or a
successful collection run. Setting `DEMO_MODE=<profile>` must serve the profile
under `fixtures/`, require no credentials, satisfy the onboarding gate, mark
every API response as demonstration data and log the fact unmissably at startup;
with `DEMO_MODE` unset the server must behave exactly as it did before. Ship two
hand-authored profiles whose every value is obviously synthetic, a persistent
non-dismissible banner in the dashboard driven by the API response rather than a
build-time constant, and a recorder that turns a live collection into a fixture
while redacting by default and failing closed on anything it does not recognise.

## Decisions and trade-offs

### The interception layer, and why it is not the Graph client

**I intercepted at the collector-dispatch layer in `backgroundRefresh.ts`, not
at the Graph client. I disagree with the brief's recommendation, for a reason
about this codebase rather than about the principle.**

The brief's argument is right and I did not want to weaken it: intercepting low
keeps the collectors, the findings engine, the drift computation, the export
pipeline and the metric store on the real code path, so what you demonstrate is
what the product does. I went looking for that seam and it is not where the
brief expects it to be.

`graphClient.ts` is not the Graph client in any meaningful sense. `getGraphClient`
builds a `@microsoft/microsoft-graph-client` instance that **no collector uses**;
its only caller in the entire repository is `graphClient.test.ts`. Every real
outbound request goes through `fetchResourceWithRetry` in
`artifacts/api-server/src/lib/collectionIssues.ts`, which acquires its own token
via `ClientSecretCredential` and calls `fetch` directly. `collectionIssues.ts` is
not on my file list, and the standing contract is explicit that editing a file I
do not own is a defect because another agent is editing it now.

I checked the three ways round that and rejected all of them:

- **Return synthetic credentials from `getGraphCredentialValues`** (which I do
  own) and let the transport run. It does not work: `getAccessToken` then calls
  `ClientSecretCredential.getToken`, which reaches
  `login.microsoftonline.com` over `@azure/core-rest-pipeline`'s Node HTTP
  client and fails. Demonstration mode would be a tenant where every collector
  errors.
- **Monkey-patch `globalThis.fetch`** from a file I do own. This is a global
  mutation in a product that holds tenant credentials, and it still does not
  solve token acquisition, because the Azure identity pipeline does not use
  `fetch`. Rejected on both counts.
- **Serve canned API responses per route.** This is the option the brief
  correctly dismisses: it bypasses the whole product and demonstrates almost
  nothing.

So the choice was between the layer above the transport and not delivering. I
took the layer above the transport, and it is closer to the brief's intent than
"short-circuit each collector" sounds. `runTask` in `backgroundRefresh.ts`
replaces one call — `task.collect()` — with a fixture read, and writes the result
through the same `metricStore.set`. Everything downstream is the production code
path: the metric store, `getOrFetch` in every route, the findings engine and all
its rules, `recordScan`, the snapshot and findings archives, drift, framework
coverage, and the CSV/XLSX/PDF/HTML export pipeline. The verification below shows
97 findings generated by the real rule set from the real store, and a real PDF
and two real workbooks.

**What I gave up.** The collectors themselves — the ~20 modules that turn Graph
JSON into a snapshot — are the one layer demonstration mode does not exercise. A
defect in a collector's transform would not show up in a demonstration, and T12's
harness cannot use these fixtures to test collectors. That is a real cost and I
would take the brief's layer if I owned `collectionIssues.ts`. **The follow-up is
small and worth doing: give `fetchResourceWithRetry` and `getAccessToken` a
fixture-backed branch, change the fixture format from collector outputs to
recorded Graph responses keyed by URL, and the collectors come back onto the
path.** Nothing else in this task would need to change; the switch, the routes,
the banner and the recorder all sit above that seam.

I did put the outbound block where the brief asked for it, because that part is
achievable in `graphClient.ts` and is worth having independently:
`getGraphCredentialValues` is what `getAccessToken` must call before it can issue
any request, so refusing there makes an outbound call in demonstration mode
impossible rather than merely unnecessary. It throws rather than returning
nothing, so a path that still expects a live tenant fails visibly.

### The fixture format is collector output, not recorded Graph responses

Follows from the layer above. A snapshot file is exactly what a collector
returns, which is also exactly what the matching route serves — so the files are
readable against `lib/api-spec/openapi.yaml` and I could validate all thirty-six
of them against it (see verification). The brief asked for "recorded Graph
responses keyed by request", which would have been right for the transport seam
and is wrong for this one. The manifest carries the name, description, schema
version, date recorded, and two fields I added: `synthetic` (whether every value
was invented) and `source` (free text for a reviewer). `synthetic` is not
decoration — the startup banner prints "NO — recorded from a real tenant and
redacted" when it is false.

### The data is generated by a committed script rather than typed by hand

`fixtures/build.mjs` is committed next to the JSON it writes. Hand-typing 653 kB
across forty files would have been slower and less reviewable: a reviewer asking
"where did this figure come from, and is it really invented?" can read one 1,300
line script instead of auditing forty JSON files. It is deterministic (seeded
Mulberry32), so re-running it is a no-op diff and the fixtures cannot drift from
the script. The cost is one more file to keep in step if a collector's output
shape changes; the schema validation in the verification section is how that gets
caught.

### Every display name carries a "(demo)" suffix

This is the anti-misuse choice and it costs some polish. `Bela Marlowend (demo)`
and `Microsoft Teams (demo)` are less convincing than clean names, and a
demonstration is meant to be convincing. I took the trade the brief asks for —
"design against that, not against tidiness" — because the suffix is the only
marker that survives the one path the banner does not cover: a PDF or spreadsheet
export, opened later, with no server anywhere near it. Every row of every export
now says `(demo)`.

Domains are under the RFC 2606 `.example` TLD so they cannot resolve or receive
mail. Identifiers are readable `demo-user-0001` strings rather than GUIDs, so
nothing in the tree can be pattern-matched as a real object id — I chose this
over generating obviously-fake GUIDs because a GUID is unreadable and therefore
unverifiable by eye.

### The response flag is injected by middleware, not added to each route

There are twenty-six routers. Editing each one was both outside my file list and
the wrong shape: a route added next month would silently ship unflagged. One
middleware wraps `res.json` and adds `demoMode`, and sets an `X-Demo-Mode` header
so a body-less observer can still tell. The trade-off is that a body that is not
a plain object (an array, a binary export) gets only the header — there is
nowhere to put a property. In practice every JSON route on this API returns an
object.

### Three routes are answered from the fixture rather than left to fail

`GET /onboarding/status` had to be, or the dashboard routes every visitor to
onboarding and never renders. `GET /m365/demo-mode` is new and is what the banner
reads. `GET /m365/connection-test` is the judgement call: it is not a gate, but
left alone it puts a red "credentials not configured" panel on the Overview tab
of an otherwise complete demonstration, which reads as a broken product rather
than a tenant-free one. All three are mounted ahead of the live handlers and all
three call `next()` when `DEMO_MODE` is unset, so the live handlers are
untouched. They live in my own file rather than in the routes they shadow.

### The banner renders nothing while its query is in flight

The alternative — assume demonstration mode until told otherwise — would show a
false "this is not real data" banner on every live tenant for a few hundred
milliseconds. That is worse, and the window it leaves open needs the page to have
rendered its data anyway, which it cannot have done before the first API response
lands. Documented in the component.

### The redactor's passthrough list is exhaustive, not pattern-based

496 field names, derived by parsing `lib/api-spec/openapi.yaml`. A pattern-based
allowlist (`/Count$/`, `/^is[A-Z]/`, …) would have been a tenth of the size and
would have failed the wrong way: a field a pattern does not match yet is a field
that travels. The cost is that the list must be regenerated when the spec gains a
field, and until then that field is dropped with a warning — which is the
behaviour the brief asked for, and which the verification below shows catching a
genuine spec gap on its first run.

I redact `department` and `jobTitle` as free text even though the brief did not
list them. In a sixty-person tenant, "Facilities Manager, Procurement" is
identifying.

## What I did not do

- **I did not intercept at the Graph transport.** Reasons above. The collectors
  are the one layer demonstration mode does not exercise, and T12 cannot use
  these fixtures to test collector transforms. I did not edit
  `collectionIssues.ts`, `concurrency.ts` or any collector, because I do not own
  them.
- **`GET /m365/groups` and `GET /m365/groups/:id/device-members` are not
  fixture-backed.** They call Graph live from the route rather than through the
  metric store, and `m365Groups.ts` is not on my file list. In demonstration mode
  they return `{ groups: [] }` / `{ deviceNames: [] }`. This affects one thing:
  the group-search box on the Intune tab, which only fires when a user types in
  it, returns no results. Every other part of that tab is fixture-backed. The fix
  is a two-line short-circuit in `m365Fixtures.ts` plus a `m365-groups` snapshot
  key; I left it because the search box is not part of the demonstration and I
  would rather not invent a route contract another agent may be changing.
- **The exports carry no demonstration watermark.** A PDF or workbook generated
  in demonstration mode is identified only by the `(demo)` suffix on every name
  in it. A page-level "DEMONSTRATION DATA" header would be better and lives in
  `artifacts/api-server/src/lib/export/`, which I do not own. Raised as a
  follow-up below.
- **I added no tests.** T12 owns test configuration and test files, and the brief
  puts them out of scope. `createRedactor` is exported from `exportFixture.ts`
  specifically so T12 can exercise it, and `resetFixtureCache()` is exported from
  the loader for the same reason.
- **I did not touch the Dockerfiles or `docker-compose.yml`.** Running
  demonstration mode in a container needs the fixture tree mounted and
  `DEMO_FIXTURES_DIR` set, which the README documents but the compose file does
  not do for you.
- **I did not fix the pre-existing lint failure** in
  `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`. See below.

## Risks and follow-ups

### The obvious one: this makes a convincing fake screenshot easier to produce

It does, and that deserves a direct answer rather than a reassurance. Before this
change, producing a screenshot of a tenant that does not exist meant editing an
image. After it, it means running one command. The feature would be worthless
without that — a demonstration nobody believes demonstrates nothing — so the
question is not whether the risk exists but what stands between a demonstration
and a fraudulent assessment.

**What I built to make misuse hard:**

- The banner is fixed to the top of the viewport, reserves its own height and has
  **no close control and no dismissed state**. There is nothing to click and
  nothing a reload could restore, so removing it from a screenshot requires
  cropping the image, which is a deliberate act of falsification rather than a
  UI interaction.
- The flag is read from the API response, not compiled in, so a production build
  pointed at a demonstration server still shows it. There is no build
  configuration that produces an unbannered demonstration.
- **Every display name in both fixtures ends in "(demo)"**, and the tenant is
  named "Fabrikam Joinery (demonstration fixture)". This is the marker that
  survives export: a PDF or spreadsheet, opened a week later with no server
  involved, still says so on every row. It is also the marker a cropped
  screenshot keeps.
- Every domain is `.example` and cannot resolve. Anyone checking the tenant's
  domain finds it does not exist.
- Every API response carries an `X-Demo-Mode` header and a `demoMode` property,
  so any automated consumer or proxy log can tell.
- The startup log is a boxed warning, not an info line, and repeats the warning
  when the fixture finishes loading.

**What remains a matter of user discipline, honestly:**

- A cropped screenshot defeats the banner. Nothing in a web application can stop
  that.
- The exports carry no watermark of their own beyond the `(demo)` suffixes. **I
  consider this the largest residual gap**, and it is the one follow-up I would
  do first: a "DEMONSTRATION DATA — NOT AN ASSESSMENT" header on every PDF page
  and a first row on every worksheet. It belongs in
  `artifacts/api-server/src/lib/export/`, which I do not own.
- Someone recording their own fixture can name it and its users anything they
  like, including something that looks real. The `(demo)` discipline is a
  property of the two committed profiles, not of the format, and the recorder
  does not enforce it. Worth considering: have `exportFixture.ts` append a
  "(demo)" suffix to every generated name, which would extend the guarantee to
  recordings.
- The `synthetic: false` flag on a recording is honest at the moment of
  recording and is not re-verified afterwards. Nothing stops someone editing it.

### Other follow-ups

- **Move the interception to the transport.** As set out above: give
  `fetchResourceWithRetry`/`getAccessToken` in `collectionIssues.ts` a
  fixture-backed branch and change the fixture format to recorded Graph responses
  keyed by URL. That puts the collectors back on the demonstrated path and lets
  T12 test collector transforms from fixtures. Everything else built here sits
  above that seam and would not change.
- **`specificPeopleLinks` is returned by the sharing-summary collector but not
  declared in `lib/api-spec/openapi.yaml`.** Found by the recorder's fail-closed
  rule. Either add it to the spec or stop returning it; until then it is dropped
  from any recording, and the sharing-summary endpoint is the one snapshot the
  schema validation has to skip.
- **`/api/m365/groups` is not fixture-backed** and returns an empty list in
  demonstration mode. Small fix in `m365Fixtures.ts` plus a `m365-groups`
  snapshot key, deferred because `m365Groups.ts` is outside my file list.
- **The recorder's `PASSTHROUGH` list must be regenerated when the OpenAPI spec
  gains a field.** Until it is, the new field is dropped with a warning, which is
  the safe direction but is a maintenance obligation. Worth a test in T12's scope
  that fails when the spec and the list diverge.
- **Demonstration mode in a container needs the fixture tree mounted** and
  `DEMO_FIXTURES_DIR` set. The README says so; `docker-compose.yml` does not do
  it, and I did not change it.
- **The pre-existing lint failure** in `emailAuthDns.test.ts` blocks the gate for
  every agent on this branch and should be fixed by whoever owns that file.
