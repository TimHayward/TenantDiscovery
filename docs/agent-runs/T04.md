# T04: Secrets at rest and optional API authentication

## Objective

Two paired security items from the backlog (2.1 and 6.4). First, the two files
this tool writes to disk were under-protected: `onboarding-settings.json` holds
the Azure client secret in cleartext and applied `chmod 0600` only on
non-Windows platforms, while `metrics.db` holds full tenant personal data and
had no permission hardening on any platform. Second, the API is unauthenticated
by design, which is a sound choice on loopback and an unsound one the moment an
operator sets `ALLOW_REMOTE=true`. I was asked to close both: a single
cross-platform file-hardening module called at file-creation time from both
call sites, and an optional bearer token enforced only when the server is bound
off loopback, with rate limiting on the authentication path. The overriding
constraint was that the default loopback developer experience must not change
at all. I was also asked to evaluate Windows DPAPI for the secret value itself
and, on the expected finding that it needs a native module, to record the
decision and the residual risk in the README rather than adding the dependency.

## Decisions and trade-offs

**Authentication is keyed on the bind address, not on a switch.** The brief
required loopback behaviour to be byte-identical. I read `HOST` in `app.ts`
exactly as `index.ts` reads it (`process.env.HOST?.trim() || "127.0.0.1"`) and
mount the middleware only when `isLoopbackHost` is false. On the default path
the middleware is never constructed, so there is no per-request cost and no new
branch in the request pipeline. The cost of this choice is a second reading of
`HOST`: `app.ts` and `index.ts` now both derive the bind host independently, and
a future change to how `index.ts` resolves it would have to be mirrored. I could
have avoided that by having `index.ts` build the app, but `index.ts` is
explicitly out of my scope, so duplicating four tokens of logic with a comment
pointing at the other reader was the smaller evil. Flagged as a follow-up.

**Surfacing the token without touching the onboarding route.** `routes/onboarding.ts`
is not mine, and Part C needs the token to appear in the onboarding response
exactly once. Rather than editing the route, I made `patchOnboardingSettings`
return `PatchedOnboardingSettings`, which carries a transient `issuedApiToken`
that is never written to disk, and taught `redactOnboardingSettings` (which the
route already calls on the patch result) to surface it. The upshot is
structural rather than conditional: because the field only exists on the value
returned from the call that generated the token, no code path that loads
settings from disk can produce it. `redactOnboardingSettings` also now strips
the stored `apiToken` via rest destructuring rather than spreading the whole
object, which fixes the latent hazard that the previous `...settings` spread
would have leaked any secret field added later. The trade-off is that the API
response gained two fields without a corresponding change to the `api-zod`
schema; the route does not validate its responses, so nothing breaks, but the
contract is now documented only in the README and the TypeScript interface.

**`timingSafeEqual` over SHA-256 digests.** `crypto.timingSafeEqual` throws on
unequal-length buffers, so comparing raw tokens would either throw (a 500 that
also confirms the length was wrong) or require a length check that leaks the
expected length. Hashing both sides first yields two 32-byte buffers
unconditionally. This is the standard construction and costs one hash per
request on a path that only exists off loopback.

**Rate limiting is per client address, and that is a real trade-off.** A fixed
window of ten failures per minute keyed on `req.ip`, with a success clearing the
count. It needs no dependency and makes guessing a 256-bit token pointless. But
`req.ip` is the socket peer unless `trust proxy` is configured, which it is not.
Behind the dashboard's nginx proxy every request would share one address, so an
attacker on the same path could lock out legitimate users for up to a minute.
I judged that acceptable because the limiter exists to stop brute force and the
lockout is short and self-healing, but a reviewer should know that I chose
availability-under-attack as the thing to give up. The alternative, keying on
the presented token, is worse: it makes brute force trivially parallel.

**Fail closed with 503, not 401, when no token is configured.** A non-loopback
bind with no token cannot be satisfied by any credential the client could send,
so 401 would be misleading. 503 with a log line naming the two remedies
(complete onboarding on loopback, or set `API_AUTH_TOKEN`) tells the operator
what actually went wrong. The trade-off is that 503 is slightly more
informative to a scanner than a flat 401.

**Only `/api/healthz` is exempt.** Not `/api/healthz/with-metadata`, which
carries more than a liveness bit and which nothing probes. `OPTIONS` is also
exempt, because a CORS preflight carries no `Authorization` header by design and
401-ing it would break the request it is asking about; a preflight discloses
nothing.

**The token is re-read from disk on every authenticated request.** The
alternative was a cache, which would mean a token generated during onboarding
did not take effect until restart, or a cache invalidation hook into
`setupConfig`. A JSON parse of a small file is immaterial next to the Graph
calls these routes make, and it buys the property that onboarding takes effect
immediately. There is a test asserting exactly that.

**Redaction was extended in `app.ts`, not `logger.ts`.** `logger.ts` is not in
my file list. pino fixes its redaction paths when the logger is constructed, so
I could not add paths to the existing logger from outside it. I used
`logger.child({}, { redact: [...] })` for the HTTP logger, which does accept
redaction options; because child options replace rather than merge, the six base
paths are re-stated alongside the four token paths. That duplication is a
maintenance smell and is called out as a follow-up: the right home for these
paths is `logger.ts`. In practice this is defence in depth rather than the
primary control, since the existing request serializer already emits only
`id`, `method` and `url` and never headers or bodies.

**Hardening `metrics.db` is guarded by an existence check.** libSQL creates the
file lazily on the first statement, and can be pointed at a database that is not
this path at all (the test fixture redirects it to `:memory:`). Without the
guard every store test would spawn a doomed `icacls` and log a warning, which
would train a reader to ignore that warning. The check is technically
time-of-check-to-time-of-use, but the action only ever tightens permissions, so
there is no security consequence.

**The WAL and shared-memory sidecars are not hardened.** libSQL may create
`metrics.db-wal` and `metrics.db-shm` beside the database, and they contain the
same tenant data. They do not exist at the moment `initClient` runs, so
hardening them there would only produce spurious warnings. This is a genuine
gap, recorded under Risks rather than quietly fixed, because fixing it properly
means hardening on a different trigger than file creation and that is a design
change beyond this brief.

### The DPAPI decision

I evaluated encrypting the client secret with Windows DPAPI (`CryptProtectData`)
and concluded it should not be done, which matches the brief's expectation. Node
has no built-in binding, so every route to DPAPI (`node-dpapi`, `koffi`,
`ffi-napi`, `win32-api`) is a native module. That conflicts with this project's
dependency posture on two counts: `pnpm-workspace.yaml` sets
`minimumReleaseAge: 1440` and maintains an explicit `onlyBuiltDependencies`
allowlist specifically to limit what may execute at install time, and a native
DPAPI module would have to be added to that allowlist. It would also do nothing
in the shipped Docker image, which is `node:24-slim`, where DPAPI does not
exist.

The decisive argument is not the dependency, though, it is that DPAPI would buy
very little. DPAPI in user scope decrypts transparently for anything running as
that user. That is precisely the same boundary the owner-only file permissions
already draw. Encrypting the secret would therefore add protection against
essentially one scenario the ACL does not already cover, an offline read of the
disk by a different account, which full-disk encryption addresses far better and
at the right layer.

**The residual risk, stated plainly: anything running as the account that runs
this server can read the Azure client secret and the API token in cleartext, and
can therefore authenticate to Microsoft Graph as the app registration and read
everything the tenant has consented to.** File permissions protect these secrets
from *other* local accounts, from a careless backup, and from a file share; they
do not protect them from the user themselves, from a local administrator, from
any malware running in that user's session, or from anyone who can read the disk
offline. I have written this into the README in those terms rather than in terms
that imply the permissions are a defence against local compromise.

I did not add the dependency and am not proposing it.

## Risks and follow-ups

**What an attacker with local user-level access can still do: quite a lot.**
Nothing in this task changes that, and the README should not be read as claiming
otherwise. An attacker running as the account that runs this server can read
`onboarding-settings.json` and therefore holds the Azure client secret and the
API token in cleartext. With the client secret they can authenticate to
Microsoft Graph as the app registration directly, from anywhere, bypassing this
API entirely, and read everything the tenant has consented to: the full user
directory, mailbox settings, device inventories, sign-in and admin role
assignments. With the API token they can reach any exposed instance of this
server. They can also read `metrics.db`, which already holds collected tenant
personal data, and they can simply modify the code or settings, since those are
owned by the same account. The permissions added here raise the bar against
*other* local accounts, against a backup or file share picking the files up, and
against the previous state where `metrics.db` was readable by anything on the
box. They do not defend the same-user boundary and cannot. The credible
mitigations are full-disk encryption, keeping the client secret short-lived and
rotated in Entra, and preferring a certificate or managed identity over a shared
secret entirely. The last of those is worth a backlog item.

**The Docker image is currently unable to start, and this is not my change.**
`artifacts/api-server/Dockerfile` sets `HOST=0.0.0.0` but neither it nor
`docker-compose.yml` sets `ALLOW_REMOTE`. `assertSafeBinding` therefore throws
and `index.ts` exits 1. Compose has `depends_on: service_healthy` for the
api-server, so the dashboard would never start either. This predates my work and
both files are outside my scope. It becomes more pressing now: once someone adds
`ALLOW_REMOTE=true`, my middleware activates, and the container will also need
`API_AUTH_TOKEN` set or it will answer 503 to everything except the health
probe. The health check itself calls `/api/healthz` and is exempt, so it will
pass, which means a misconfigured container would look healthy while serving
503s. Whoever fixes the `ALLOW_REMOTE` gap should add `API_AUTH_TOKEN` to the
compose environment in the same change, and should note that the dashboard's
nginx proxy will need to attach the header.

**The dashboard does not yet show the token.** Deliberate, per the brief, but it
means the one-time reveal currently has no consumer. Until the UI is updated, an
operator onboarding through the dashboard never sees the token and must recover
it by clearing `apiToken` from the settings file. This should be the first thing
picked up in the next wave.

**`metrics.db-wal` and `metrics.db-shm` are not hardened.** They hold the same
tenant data as the database. They do not exist when `initClient` runs, so this
needs a different trigger than file creation. Worth a follow-up.

**`req.ip` without `trust proxy`.** As described above, behind the nginx proxy
all clients share one address for rate-limiting purposes. If the API is ever
exposed behind a proxy in earnest, `trust proxy` should be configured and the
limiter key revisited; note that enabling `trust proxy` naively lets a client
spoof `X-Forwarded-For` and evade the limit entirely, so it needs the hop count
set correctly rather than just being switched on.

**Duplicated redaction paths.** `app.ts` now re-states the six redaction paths
from `logger.ts` because pino child options replace rather than merge. The right
fix is to move all ten paths into `logger.ts` and drop the child, which I could
not do within my file list. Small, but it will drift.

**`HOST` is read in two places.** `index.ts` and `app.ts` each derive the bind
host. If the resolution rule changes in one, authentication silently stops
matching the binding. A shared helper would fix it, but it would have to live
somewhere both can import, and `index.ts` was out of scope.

**The API response gained fields the zod schema does not describe.**
`apiToken`, `apiTokenNotice` and `hasApiToken` are returned by the onboarding
routes but `@workspace/api-zod` has no matching schema change. Nothing validates
these responses, so nothing breaks, but the generated client types will not know
about them. Worth aligning when the dashboard work happens.

**No token rotation endpoint.** Recovering a lost token means editing the
settings file by hand. Acceptable for a tool that is loopback-only by default,
but if remote use becomes common a rotation route would be wanted, and it would
need to be authenticated with the current token.

including two full runs of the five gate commands, a full build, and two real
server runs for the end-to-end verification. Roughly a third of that was the
verification rather than the edits.

Token cost: not available to me in this environment.
