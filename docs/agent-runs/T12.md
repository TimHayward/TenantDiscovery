# T12: Dashboard test harness

## Objective

Nineteen thousand lines of dashboard had no test infrastructure of any kind, so
every convention that governs a dashboard test was unset: where a test file
lives, how the generated React Query hooks are stood in for, how a Radix
component is driven inside jsdom, and what a test that is worth keeping looks
like. Those decisions were the deliverable, not coverage. The task was to build
the harness — Vitest, jsdom, Testing Library, MSW against the HTTP layer rather
than against the hooks, response bodies validated against the generated Zod
schemas and read out of T10's demonstration profiles — to prove it works on a
small number of high-value paths, to wire it into the package's `test` script
and into CI, to write the pattern down including the traps, and to report the
resulting coverage plainly rather than choosing a subset that flatters it.

## Decisions and trade-offs

### MSW against the HTTP layer, not mocks against the hooks

This is the brief's instruction and I agree with it, but it is worth recording
what it costs, because the cheaper option is genuinely cheaper.

Mocking `useGetM365OverviewWithMetadata` would have made every test in this
suite two lines shorter and would have removed the four traps in the "jsdom"
section below entirely — no MSW, no undici, no abort-signal mismatch, no
relative-URL problem. What it also removes is the generated client, its response
parsing, its error construction and the React Query cache, which between them
are most of what can actually break between the server and a rendered figure.
A hook mock asserts that a component renders a literal written two lines
earlier.

The concrete payoff showed up immediately in the error test: the message the
`ErrorPanel` displays comes off the response body through the generated client's
`ApiError`, so `expect(screen.getByText(/The metric store is unavailable\./))`
covers the whole path from an HTTP 500 with a problem body to rendered text. A
hook mock would have covered none of it.

The cost is a slower suite (roughly 8 seconds standalone against perhaps 2 for
the mocked equivalent) and four pieces of environment plumbing that had to be
diagnosed once. Both are one-off.

### Bodies validated at handler construction, not at request time

`ok()` validates when the handler is built, so a fixture that no longer fits the
contract throws at the `server.use(...)` line with the field named. Validating
inside the resolver was the alternative and would have been worse: a rejected
resolver becomes a 500, the component renders its error panel, and the test
fails three assertions later with no mention of the schema. Loud beats close.

The schemas are left non-strict, which means an extra field passes. That is a
deliberate concession to an existing divergence rather than laziness: several
routes return `partialData`, `permissionError` and `collectionIssues`, the
committed snapshots carry them, and the OpenAPI document does not declare them.
A strict schema would have failed on that divergence on the first run and I
would have had to strip fields out of the fixtures to get green, which would
have removed exactly the data that `summarizeIssues` reads. It is recorded as a
follow-up.

`ok()` also serves the original body rather than the parsed output, for the same
reason: a `zod.object` strips undeclared keys, so serving the parse result would
have silently deleted `collectionIssues` from every response.

### Bodies come from T10's profiles, not from bodies written here

The brief asked for this if T10 had landed, and it has. `snapshot("m365-overview")`
reads `fixtures/healthy-mid-market/snapshots/m365-overview.json` off disk. The
tests and `DEMO_MODE=healthy-mid-market` therefore show the same tenant, with
one place to maintain it.

Two things had to be built on top. The `with-metadata` envelope is assembled per
field by each route, so `withMetadata()` derives a uniform entry from the
snapshot's own keys — a component only needs an entry to exist for a field it
asks about, and a test that cares about a particular evidence status should say
so at the call site rather than inherit whatever the server claims today.
`/api/onboarding/status` and `/api/m365/connection-test` have no snapshot at all,
because the fixture route synthesises them; those two are restated in
`fixtures.ts`, matching `m365Fixtures.ts`, and are validated against the same
schemas as everything else.

Assertions read values off the fixture rather than repeating them
(`String(overview.totalUsers)` rather than `"250"`), so a revision to the profile
does not break the tests while a component reading the wrong field still does.

### Where tests live

`__tests__` beside the subject, matching the api-server. Shared machinery in
`src/test/`. The alternative — a top-level `tests/` tree mirroring `src/` — was
rejected because it puts a test and its subject far apart in every file listing
and in every review diff, and because there was already one convention in this
repository and no reason for the dashboard to have a second.

`src/test/` sits inside `src/` rather than beside it so that the package's
`tsconfig.json` typechecks it without modification. That file is not this task's
to edit, and its `include` is `src/**/*`.

### `globals: false`

Consequence of the same constraint. The package's `tsconfig.json` fixes `types`
to `node` and `vite/client`, so ambient `describe`/`it`/`expect` would not
typecheck, and adding `vitest/globals` there would have been an edit to a file
outside my list. Every test file imports them from `vitest` instead. The cost is
one line per file; the second-order cost is that Testing Library's automatic
cleanup no longer registers itself, so `setup.ts` calls `cleanup()` by hand.

### The four jsdom gaps

Each is documented at the site of its fix and in `docs/testing-the-dashboard.md`;
the reasoning behind the two non-obvious ones belongs here.

**Abort primitives.** jsdom implements `AbortController` and `AbortSignal` and so
replaces Node's; jsdom does not implement `fetch`, so the global `fetch` stays
undici's; undici rejects the jsdom signal React Query supplies, and the request
fails with `Expected signal ("AbortSignal {}") to be an instance of AbortSignal`.
In a component test that surfaces as an error panel, which reads as a bug in the
component. I chose a five-line custom Vitest environment that installs jsdom and
then restores Node's two constructors. The alternative — stripping the signal in
a `fetch` wrapper — is shorter and would have made every request in every test
uncancellable while quietly diverging from the browser, which is the kind of
difference that makes a suite stop predicting production.

**Relative URLs.** Node's `fetch` will not parse `/api/m365/overview`. The shim
has to wrap MSW's `fetch` rather than the other way round, because MSW builds a
`Request` before consulting any handler and that construction is what throws, so
it is installed after `server.listen()`. Calling `setBaseUrl()` from
`@workspace/api-client-react` was the tidier-looking option and was rejected
because it covers the generated client but not `lib/onboardingApi.ts` or
`DemoModeBanner`, which call `fetch` directly.

**Layout and ResizeObserver.** Recharts' `ResponsiveContainer` reads
`getBoundingClientRect()` and renders `null` below a positive width, and
constructs a `ResizeObserver` unconditionally. Without the first, chart
assertions would be vacuous rather than failing; without the second, chart tabs
crash on mount. Both are stubbed in `setup.ts`.

### How keep-alive is asserted, and what had to be given up

The inactive tab is hidden by a Tailwind `hidden` class. No stylesheet is loaded
in jsdom, so nothing in the environment can tell hidden from visible, and
`toBeVisible()` returns true for both. Asserting `toHaveClass("hidden")` would
have been available and is exactly what the documentation's "do not do this"
section forbids, so it was not used.

What is asserted instead is stronger in the way that matters: the first tab is
still in the document after switching away, *and* it has not issued a second
request for its data. The test `QueryClient` has a zero `staleTime` and a zero
`gcTime`, so a remount would certainly refetch, which makes a request count of
one a sharp proof that the tree was preserved. The visibility half is stated as
out of reach, in a comment, rather than faked.

The per-tab-state test went through a similar correction. My first version
collapsed a section on the Overview tab and checked it was still collapsed on
return — which would have passed after a remount too, because
`CollapsibleSection` persists that state in `localStorage`. It now uses the
licence tab's free/developer SKU switch, which is plain component state: not in
the URL, not in React Query, not persisted.

### Seventeen tests rather than ten to fifteen

The brief asked for ten to fifteen. There are seventeen. I merged where merging
lost nothing — the sort and reverse-sort cases are one test, the filter and
empty-filter cases are one — and stopped there rather than deleting real
guarantees to hit an arithmetic target. The four extra over the brief's own
enumeration are keyboard sorting, `CollapsibleSection` persistence, the
`refresh` request, and the "no banner without an issue" case folded into the
open/close test. Each guards a distinct behaviour and none of them is
coverage-driven.

### CI: comments, not a third step

The brief allocated a CI step. The root `test` script is
`pnpm -r --if-present run test`, so the dashboard's new `test` script is already
run by the existing `Test` step, and again by the `Test with coverage` step
after it. A dashboard-specific step would have been a third execution of the
same suite for no extra signal, at about twenty seconds each time. I added
comments to both steps instead, so that the absence of a dashboard step reads as
a decision rather than an oversight, and so that a reader knows where the
dashboard tests run. If the intent was specifically to have the dashboard fail
CI independently of the api-server, that is a one-line change a reviewer can
make; I did not think the attribution was worth the duplicate run.

### Timeouts

The suite passed standalone and failed from the root, on the first Dashboard
test, at Vitest's default five-second `testTimeout`. The cause is real and not a
race: tab modules are behind `React.lazy`, so the first render in a file pays to
load and transform Recharts and TanStack Table, and under `pnpm -r run test` —
where this package runs alongside the api-server's thirty files — that was
measured at over seven seconds.

I raised `testTimeout` to 30s and Testing Library's `asyncUtilTimeout` to 15s,
with the latter deliberately the smaller so that a slow wait is reported as the
element that never appeared rather than as an unexplained timeout. These are
ceilings for a pathological case rather than budgets, and both are documented as
such. The alternative of leaving the default and accepting a suite that passes
alone and fails from the root is the worst of both. I did not add a `waitFor` to
paper over it, and the documentation says not to.

## What I did not do

- **I did not cover the dashboard.** Fifteen of sixteen tabs have no test.
  Statement coverage is 13.29%. That is the brief's instruction, not an omission,
  but it should be read as what it is: the pattern is established and almost
  nothing is guarded yet.
- **I did not assert on the export request.** The brief asked for the export
  button to be proved through the request MSW received. It cannot be, as the
  feature is currently built: the export entries are plain `<a href>` anchors to
  server routes, so the browser navigates and no `fetch` is issued, and jsdom
  does not navigate at all. The test asserts the addresses and the
  `target`/`rel` pair instead, and the request-through-MSW pattern the brief
  wanted is established on the Refresh Data button, which does issue a real
  `POST /api/m365/refresh`. The change that would make the export assertable the
  same way is in the follow-ups.
- **I did not drive a Radix component with a portal.** The components the brief
  named turned out not to need one: `CollapsibleSection` is a hand-rolled toggle,
  and the export and auto-refresh menus in `Dashboard.tsx` are hand-rolled
  dropdowns, not Radix. The one Radix primitive the tests do drive is a `Switch`,
  which does not portal. `docs/testing-the-dashboard.md` documents the portal
  rule (`screen`, not `within(container)`) so that the next person adding a test
  over a `Select` or a `Popover` does not have to rediscover it, but I have not
  proved it with a test and have said so here rather than implying otherwise.
- **I did not set a coverage threshold.** I propose one below and in the
  documentation, but leaving it unset matches the api-server, and choosing a
  floor is a decision for a human who has seen the number.
- **I did not fix the pre-existing lint failure.** Six `no-explicit-any`
  warnings in `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`
  break `pnpm run lint` at `--max-warnings 0`. That file is not mine and the
  contract is explicit. It is reported honestly in the verification below.
- **I did not add `artifacts/m365-dashboard/coverage/` to `.gitignore`.**
  `.gitignore` is not on my file list and its `/coverage` entry is root-anchored,
  so per-package coverage output is untracked-but-not-ignored. The api-server has
  had the same gap since its own harness landed. Follow-up below.

Thirteen per cent is a low number and it should be read as one. It is one tab of

**Proposed starting threshold: 12% statements, 12% lines, 30% functions, no
branch threshold.**

A threshold's only job at this stage is to stop the number going backwards. Set
a point or so below the measured figure, it tolerates a refactor that adds an
untested file and trips on a deletion of tests or a large new untested tab. A
branch threshold is left off because that figure will move sharply, in either
direction, the moment a second tab is covered, and a threshold that has to be
edited every time it is approached teaches people to edit thresholds.

## Risks and follow-ups

### Components that are hard to test as they stand

Each of these is a finding, not a refactor I made.

- **The export menu cannot be asserted through a request.** `Dashboard.tsx:522-556`
  renders five `<a href="/api/m365/export/...">` anchors. A browser navigates;
  jsdom does not, and no `fetch` is issued either way, so MSW never sees them.
  The behaviour that matters — that pressing "Findings (CSV)" produces the
  findings CSV — is therefore untestable at this level. Fetching the blob and
  triggering a download from an object URL would make it assertable exactly like
  the refresh button, at the cost of losing the browser's native download
  progress and its handling of a large evidence pack. That is a product decision,
  not a test one, and worth a ticket either way.
- **`App.tsx` cannot be rendered in a test at all.** Its module scope registers
  `popstate` and `hashchange` listeners that call `window.location.reload()`
  (documented there as a workaround for a render loop originating in
  `IntuneTab.tsx`). Importing the module in a test environment installs those
  listeners globally for the rest of the file. The Dashboard tests reproduce
  `App.tsx`'s single route rather than rendering `App`, which means the routing
  in `App.tsx` — the `/` redirect, the unknown-tab redirect, the onboarding gate
  — is not covered and cannot be until that workaround is removed. The render
  loop it works around is the real ticket.
- **`ConnectionTestPanel` has no accessible name on its section.** It is found by
  its title text. Not a defect, but a `DataTable` with two instances on a page
  would be genuinely ambiguous to query; `aria-label` on the tables inside tabs
  would pay for itself the first time two are tested together.
- **`Skeleton` is unidentifiable.** `lib/ui-kit/src/skeleton.tsx` renders a bare
  `div` with utility classes and nothing else, so a loading state can only be
  asserted negatively ("no figure is shown yet"), which is what the OverviewTab
  loading test does. A `role="status"` with an `aria-label`, or a `data-slot`,
  would make the positive assertion available and would also announce loading to
  a screen reader, which it currently does not.
- **`IntuneTab.tsx` is 2,479 lines and `UsersTab.tsx` 1,127.** Not untestable,
  but a first test over either will be expensive, and the mount cost will show
  up in the suite time. Whoever covers them should expect to split them first.

### Other things a human should look at

- **The OpenAPI document does not declare `partialData`, `permissionError` or
  `collectionIssues`,** although several routes return them and the dashboard
  reads them (`summarizeIssues`, `getCollectionIssues`, the KPI issue treatment).
  Because they are absent from the spec, they are absent from the generated Zod
  schemas and from the generated TypeScript types, so nothing checks them
  anywhere. That is why the handler validation is non-strict. Adding them to the
  spec would let the validation be tightened and would type the fields the issue
  banners depend on.
- **Per-package `coverage/` is not gitignored.** `.gitignore` has a
  root-anchored `/coverage`, so `artifacts/m365-dashboard/coverage/` and
  `artifacts/api-server/coverage/` are untracked but not ignored, and a developer
  who runs coverage locally will see them in `git status`. One line fixes it;
  `.gitignore` was not on my file list.
- **`GetOnboardingStatusResponse` is missing fields the dashboard reads.** The
  schema declares neither `missingRecommendedPermissions` nor
  `allRequiredPermissionsMissing` nor `canContinueWithMissingPermissions`, all of
  which `Dashboard.tsx` and `OnboardingPage.tsx` use. The fixture carries them
  and validation tolerates them; the spec should not.
- **The `asyncUtilTimeout` and `testTimeout` values are generous** and will hide
  a genuine hang for up to thirty seconds. They are sized for the lazy-tab first
  render under a loaded machine, which is a real cost, but if the suite is ever
  split so that tab modules are warm, both should come back down.
- **`fixtures.ts` resolves the fixture tree by a relative path**
  (`../../../../fixtures`). The api-server's loader supports a `DEMO_FIXTURES_DIR`
  override; the test helper does not. Moving either the fixtures or the package
  breaks the tests with a clear message but breaks them nonetheless.
