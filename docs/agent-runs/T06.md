# T06: Bundle budget and request-path efficiency

## Objective

Two related pieces of work. The dashboard shipped a 420 kB Recharts chunk that
was pulled in eagerly by the entry chunk, so every visitor downloaded and
executed the whole charting library before any tab rendered, including a
visitor going straight to Settings, which renders no chart. The task was to
rework the chunking so a chart-free tab downloads no charting code, and to add
a bundle budget that stops the improvement regressing. On the server side, the
task was to remove repeated work from the export and findings request paths:
push the findings filters into SQL, replace a loop of awaited inserts with a
batch, compute the framework coverage once per export, de-duplicate
`SEVERITY_RANK`, resolve the two byte-identical xlsx handlers, and stop the
`PATCH` route reading the whole register to return one row.

This closes the remainder of backlog 6.7 and all of 5.6.

## Decisions and trade-offs

### The chunking choice, with the numbers that drove it

The brief listed two options and asked for the deciding evidence. I took option
1, deleting the `manualChunks` rules entirely, because the measurement showed
the duplication cost the brief warned about does not exist here.

The diagnosis first, because it is not what the brief's framing implied. The
`charts` chunk was not merely failing to be lazy; it was **statically imported
by the entry chunk**. Because `charts`, `tables` and `radix` were shared by the
application shell and by several tabs, Rollup had to make the entry import them
eagerly to preserve module execution order. The eager payload was therefore
`index + charts + tables + radix`. The lazy tab split was working exactly as
designed and was being entirely undone by three lines of configuration.

Measured on this tree, in Vite's units (kB = 1000 bytes), where "cold X" is the
entry chunk plus its transitive static closure plus the closure of tab X:

| Metric | Before | After | Change |
| --- | --- | --- | --- |
| Eager entry payload | 930.95 kB / gzip 269.54 kB (4 chunks) | 405.97 kB / gzip 127.22 kB (1 chunk) | **−524.98 kB / −142.32 kB** |
| Cold Overview total | 955.83 kB / gzip 280.06 kB | 814.98 kB / gzip 244.44 kB | −140.85 kB / −35.62 kB |
| Cold Settings total | 1058.89 kB / gzip 291.37 kB | 533.79 kB / gzip 148.98 kB | **−525.10 kB / −142.39 kB (−49.6%)** |
| Cold Findings total | 945.49 kB / gzip 275.11 kB | 420.37 kB / gzip 132.71 kB | −525.12 kB / −142.40 kB |
| Settings after Overview | 122.58 kB / gzip 19.61 kB | 122.50 kB / gzip 19.56 kB | −0.08 kB |
| Total emitted JS | 1425.69 kB / gzip 393.88 kB | 1425.77 kB / gzip 398.73 kB | +0.08 kB raw, +4.85 kB gzip |

The decisive line is the last one. Total emitted JavaScript is unchanged to
within 0.08 kB, so **letting Rollup duplicate cost nothing at all**: there is no
duplication to trade against the eager download saved. The brief predicted the
duplication would usually be cheaper than the eager download; here it is free.
The only cost is 4.85 kB of gzip across the whole output, because the same bytes
split across more, smaller chunks compress marginally worse. That is 1.2% of the
compressed total, against 142 kB saved on every cold visit.

Settings is the case the brief asked about specifically: **1058.89 kB → 533.79
kB, a 49.6% reduction**, and Recharts is no longer in its download at all. Its
remaining 122.50 kB beyond the entry is almost entirely the 117.81 kB
permissions manifest, which Settings genuinely renders.

Overview improves less, 955.83 kB → 814.98 kB, and that is the honest and
expected result: Overview really does render charts, so it really does need
Recharts. The change moves that cost from everyone to the people who incur it.

### `tables` and `radix`

I measured rather than assumed. Keeping `tables` and `radix` as manual chunks
while removing only `charts` gives an eager payload of **508,528 bytes across 3
chunks**, against **404,043 bytes in 1 chunk** with all three rules removed. The
same reasoning applies to them as to `charts` and the measurement supports
removing them, so all three went. Had the numbers gone the other way I would
have kept them, per the brief's instruction not to change them unsupported.

### Budgeting the closure, not the entry file

The brief asked for a ceiling on "the entry chunk". I budgeted the eager entry
**closure** instead, and this is a deliberate deviation worth a reviewer's
attention.

Budgeting the single entry file is precisely the metric the old configuration
gamed. Before this change `index.js` was 298.01 kB, comfortably under any
sensible ceiling, while the real eager payload was 930.95 kB. A budget on the
entry file alone would have been green throughout the entire defect this task
exists to fix. The closure is the number that corresponds to what a user waits
for, so it is the number worth defending. It also strictly subsumes the entry
file, since the entry file is a member of its own closure.

The check lives in a `generateBundle` hook in `vite.config.ts` rather than as a
shell step in CI, for two reasons. It walks Rollup's own `chunk.imports`
metadata, which is the authoritative static-import graph, instead of
re-parsing minified output with a regex; and it fails local builds too, so the
budget is discovered by whoever breaks it rather than by CI afterwards. The CI
step then just runs the build.

I set the ceiling at 438,000 bytes, the achieved 404,043 plus roughly 8%. That
absorbs ordinary dependency drift but not a regression of the Recharts kind.

### The double rule evaluation the brief describes does not exist in this tree

The brief states that `getExecutiveModel` calls `getFrameworkCoverage()` twice
per export and that each call re-runs the rule set. I measured before changing
anything, with a spy on the stubbed engine, and **each export route already
triggered exactly one `evaluateFindings` call**: one for `executive.pdf`, one
for `executive.html`, one for each xlsx route. `getExecutiveModel` contained a
single `getFrameworkCoverage()` call. I could find no second call on any export
path, and the file's git history shows no commit that removed one.

I have not reported this as fixed, because there was nothing to fix. What I did
deliver is the structural half the brief asked for: `getExecutiveModel` now
takes an optional pre-computed coverage so a caller needing both the model and
the coverage table computes it once, and a test now pins one evaluation per
export request across all four export routes. That test is a guard against the
regression rather than proof of a repair, and I would rather say so than let a
green test imply a saving that was not there.

### The two xlsx handlers: collapsed, not differentiated

The brief said to differentiate them "if the export model already carries the
evidence fields", and to check before deciding. I checked, and it does not.

The evidence-bearing columns a workbook could add, Evidence, Confidence and
Source, are already in `FINDING_EXPORT_COLUMNS` and therefore already in both
workbooks. The one field that would genuinely distinguish an evidence pack is
the raw `evidence` payload, which exists on the `Finding` domain type but is
dropped by `toRow` and is not carried by the archived-scan path in `getScan` at
all. Differentiating properly would mean extending `FindingExportRow`, which
also changes the CSV column contract, and adding evidence to the scan history
schema. That is a larger change than this brief covers and it belongs in its
own task.

So I collapsed to one handler serving both routes. Each keeps its own filename
and its own failure message, so no existing client sees any change. The trade-off
is that the two URLs remain undifferentiated, which I have flagged as a
follow-up rather than papered over.

### Preserving the empty-string filter semantics

The original filters tested truthiness (`if (query.severity)`). Moving to SQL, a
naive `!== undefined` check would have changed behaviour: `category` is
`zod.coerce.string().optional()` in the query schema, so `?category=` arrives as
`""`, which previously meant "unfiltered" and would have started meaning "match
nothing". I kept truthiness for the three user-facing filters and used a strict
check only for the internal `fingerprint` lookup, where an empty value must
match nothing rather than return the whole register. Both cases are tested.

### The status filter across the LEFT JOIN

A finding with no `finding_state` row is open by definition; the old JavaScript
filter got this right via `?? "open"`. A naive `s.status = ?` in SQL would have
silently dropped every never-triaged finding from a `?status=open` query, which
is most of the register. The predicate is `COALESCE(s.status, 'open') = ?`, with
a test covering exactly that case.

### Batching `pruneOldScans` as well

The brief named only `recordScan`. `pruneOldScans` has the identical defect,
three awaited deletes per expired scan, sits in a file I own, and runs on the
same request path as part of the same operation, so I batched it too. It also
fixes a small integrity hazard: the three deletes for one scan now commit
together, so a pruned scan cannot survive as an orphaned run row with its
history already gone.

## What I did not do

- **I did not fix the pre-existing lint failure.** `pnpm run lint` was already
  failing on arrival with six `no-explicit-any` warnings in
  `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`, a T02 file I do
  not own. Per the contract I noted it and worked around it rather than fixing
  it. Evidence that it is pre-existing and untouched by me is in Verification.
- **I did not differentiate the two xlsx routes.** Reasons and the measurement
  above. They are collapsed to one handler with two routes.
- **I did not use "the existing binding-safety helper"** the brief refers to for
  the SQL work, because there is no such helper. The only binding helper in the
  repository is `assertSafeBinding`, which concerns loopback **network** binding
  and is part of the security posture I must not touch. The codebase's actual
  convention for safe SQL is `?` placeholders with a separate `args` array, used
  throughout `store.ts` and `scanStore.ts`, and that is what I followed. A test
  asserts the value is bound and never interpolated into the statement text.
- **I did not change `getFrameworkCoverage` to cache across requests.** Threading
  it through a request is in scope; a cache has invalidation semantics that need
  their own design.
- **`tables` and `radix` were examined and changed**, on the measurement above.
  The brief asked me to say what the measurement showed if I looked, and it
  showed that keeping them costs 104 kB of eager payload.
- **`CONTRACT.md` does not exist in this repository.** The brief opens by saying
  to read it first. I searched the whole tree and found no such file; the
  standing contract was supplied inline with the task, and that is what I
  followed.
- No files outside the ownership list were edited. The bundle analysis script I
  used for measurement was deliberately kept outside the repository, in a
  temporary directory, because I do not own `scripts/`.

   `pnpm run build`, which incidentally closes that gap, but a reviewer should
   know the gap existed rather than assume the step is only about the budget.
2. **The lint gate is red on `main`** because of six `no-explicit-any` warnings
   in `emailAuthDns.test.ts` with `--max-warnings 0`. Outside my scope; whoever
   owns that file should either type the mocks or the team should decide the
   rule is wrong there. Until then every agent's gate reports a failure it did
   not cause.
3. **The `evidence.xlsx` route is still undifferentiated.** Making it a genuine
   evidence pack needs `evidence` carried through `FindingExportRow` and added
   to the `findings_history` schema so archived scans can serve it too. That
   touches the CSV column contract and a migration, so it wants its own task.
4. **`useChartTheme-FyEW6Cfl.js` is a 359 kB shared chunk** named after a 0.31 kB
   module that happens to be its entry point. It is Recharts. The name is
   confusing in build output and in dev tools; a reviewer may want a stable
   explicit name for it, which can be done with `chunkFileNames` without
   reintroducing eager loading.
5. **Recharts at 359 kB is still the largest thing any charting tab downloads.**
   Nothing in this task reduces that; it only stops non-charting tabs paying for
   it. If the eager payload matters more, the next lever is a lighter charting
   library or importing only the Recharts pieces each tab uses.
6. **`chunkSizeWarningLimit: 650` is now above the largest chunk** and no longer
   warns about anything. It could be lowered, but the budget supersedes it as
   the real guard, so I left it rather than change a setting outside the brief.
7. **The budget covers JavaScript only.** The 124.80 kB CSS bundle is eager and
   unbudgeted.
8. **`getFrameworkCoverage` still re-runs the full rule set on every export.**
   Threading it through a request is done; making it cheaper across requests
   needs a cache with real invalidation, which was not in scope.

## Cost and duration

Wall-clock: approximately 1 hour 5 minutes from the arrival gate to the final
commit, against a 3 hour estimate. Token cost was not exposed to me by the
harness, so I cannot report it.

Roughly half the time went on measurement rather than editing, which was the
right split: the first version of my chunk-graph analyser had a regex that
missed minified `}from"./x.js"` imports and reported that `charts` was *not*
eagerly loaded, which is the opposite of the truth. Had I trusted it I would
have reported a much smaller improvement and misdiagnosed the defect. It was
caught by cross-checking one chunk's imports by hand against the analyser's
output, and every number in this report comes from the corrected version.
