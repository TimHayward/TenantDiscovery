# T11: Scan history and drift timeline

## Objective

The backend has archived a metric snapshot and a per-finding summary on every
scan for some time, computes drift between any two of them, and serves all three
at `/m365/scans`, `/m365/scans/{id}` and `/m365/drift`. None of it reached a
screen, so the data that turns "here is what is wrong today" into "here is
whether you are getting better" was being collected on every run and discarded
at the presentation layer. The task was to surface it as a History tab: a
severity trend across scans that survives being printed in a client report,
drift between two chosen scans that matches `computeDrift` exactly, and a
per-finding audit trail with the manual triage change interleaved. The archive
is a summary, thinner than the live view, so the second requirement of the task
was to label that gap on screen rather than let a blank archived field read as a
measured zero. Nothing outside the dashboard was to be touched.

This is backlog 6.6.

## Decisions and trade-offs

### The trend needs one request per scan, and that shaped the design

There is no endpoint that returns severity counts per scan. `/m365/scans` gives
a total `findingCount` and nothing else; the breakdown only exists inside
`/m365/scans/{id}`. So a trend over twenty scans is twenty requests, and over
the fifty the server retains by default it is fifty.

Per the brief I did not add an endpoint. What I did instead was bound the
fan-out with a window, default twenty, selectable at ten, twenty or fifty, and
say on screen how many retained scans the window left out rather than pretending
the window is the whole history. The requests go through
`getGetM365ScanQueryOptions` driven by `useQueries` rather than a hand-written
fetch, so they share the cache, the base URL, the error shape and the dashboard's
refresh-invalidation predicate with every other query; `useQueries` is only
there because a generated hook cannot be called in a loop.

The cost is real and I have not hidden it: opening the tab with the default
window issues twenty-one requests. The right fix is an aggregate endpoint, which
is written up under follow-ups.

### Colour is the least load-bearing of the three series cues

The brief says the trend view is the one that gets screenshotted into a report,
and that it has to be readable in monochrome print. Colour survives neither a
greyscale printer nor a reader with a colour vision deficiency, so each severity
carries a colour, a stroke dash pattern and a marker shape, and all three come
from one table so the chart and the legend cannot disagree about which line is
which.

I wrote the legend by hand rather than using Recharts' `<Legend>`. Recharts can
render a `plainline` icon that picks up `strokeDasharray`, but it cannot render
the marker shape, so its legend would have carried two of the three cues and the
one it dropped is the one that still works when two series sit at the same
value. A hand-drawn SVG swatch carries both.

The counts table under the chart is not a fallback for the chart's failure. Two
series at identical values overlap in any line chart, monochrome or not, and the
first question anyone asks of a trend line is what the number actually was. The
table answers both, and it is what a reader can paste into a document.

I did consider `ComposedChart` with a `Scatter` per severity, which would have
given marker shapes from Recharts' own vocabulary. I used `Line` with a custom
dot renderer instead: it is one component per series rather than two, and it
keeps the legend, the tooltip and the connect-nulls behaviour in one place. The
price is one type assertion, because Recharts declares the `dot` render prop as
returning `ReactElement<SVGElement>`, which no ordinary SVG element satisfies.
The assertion is around that declaration, not around a claim about the value,
and it is commented as such.

### Scans are spaced evenly, and the chart says so

The x axis is categorical: one slot per scan, regardless of the interval between
them. A true time axis would be more faithful, but twenty scans clustered into a
fortnight after a quiet month would compress into an unreadable smear at one
end. The trade is stated on screen next to the chart rather than left for a
reader to discover by comparing tick labels.

Tick labels are decided for the window as a whole. If every scan in the window
falls on its own day the labels are dates; the moment two share a day, every
label gains a time. Mixing the two formats within one axis makes adjacent ticks
look like different quantities.

### Failed runs are excluded from the trend and visible in the table

A run with `status` other than `completed` has a partial or empty findings
archive. Plotting it draws a fall that never happened, which in a client report
is worse than a gap. So the trend plots completed runs only, the tab says how
many it excluded and why, and the Scan Runs table shows every run including the
failed ones so the exclusion is auditable rather than silent. A scan whose
detail request fails is a null in the series, drawn as a break in the line
rather than as a zero.

### The drift view reproduces the endpoint, including its awkward parts

The three columns are `added`, `resolved` and `changed` as returned, entry for
entry. I sort within a column by severity, which is a reordering, and I show a
severity tally in each column header, which is an aggregate and is labelled
"Counted by severity".

Reading `computeDrift` turned up two behaviours that would mislead a reader who
assumed the obvious. A finding that moves from an actionable status to `pass` is
pushed into `resolved` by one loop and into `changed` by the other, so it is
reported twice and the three counts can exceed the number of distinct findings
that moved. A finding that appears for the first time already passing is
reported in none of the three. Both are on screen under the columns.

I chose not to deduplicate the overlap. Silently removing it would make this
view disagree with the API, with the export, and with the drift panel already on
the Findings tab, and a reader reconciling a screenshot against a CSV would find
a discrepancy with no explanation. Explaining it costs two sentences.

I also warn when the baseline is the later of the two scans, because the
endpoint does not care about ordering and "appeared" then reads backwards.

### The per-finding timeline draws on two sources and never merges them

Transitions come from consecutive retained scans. The register supplies its own
`firstSeen` and `lastSeen`, which it tracks independently of scan retention, and
the one triage change it keeps.

The API stores no log of triage transitions, only the current state and its
`stateUpdatedAt`. So "the manual state changes interleaved" is, at most, one
interleaved event. It is labelled "Findings register (latest change only)" so
the timeline does not read as a complete audit trail when it is not one. Every
event names its source, which is what makes the view evidenceable: a reader can
take any line and go and check it.

The two sources are shown as separate events rather than reconciled into one
first-seen date. They can genuinely disagree — the register can know about a
finding older than the oldest retained scan — and picking one would throw away
the more informative answer.

### Summary-only labelling, corrected once

My first version of the note listed seven fields as "not archived". That was
wrong for two of them. `findings_history` stores nine columns; the endpoint
returns six. Evidence status and confidence are archived and simply not served,
as are the metric snapshot payloads, of which `/m365/scans/{id}` returns only
the key list. That is a different problem with a different fix: changing one
route recovers them for every scan already recorded, whereas description,
remediation and the rest were never written and are gone. The note now names the
two groups separately, which is also what makes the storage argument below
answerable.

### Registration went slightly beyond the strict minimum

The brief says "tab registration only, minimal diff" for `Dashboard.tsx`. The
route entry, the lazy import and the icon are compile-forced by T09's design. The
four `NAV_SECTIONS` entries are not: `NAV_SECTIONS` is `Partial`, so the tab
would work without them. I added them anyway, because every other tab has them
and without them the History tab would be the only one whose sections are not
reachable or linkable from the sidebar, which is most of what T09 built. That is
five lines and a judgement call, and it is flagged here rather than buried.

I placed History after Framework Mapping so the three findings-related tabs sit
together.

## What I did not do

- **I did not add an aggregate endpoint**, and the trend therefore issues one
  request per scan. This is the brief's instruction, and the case for the
  endpoint is under follow-ups.
- **I did not add tests.** The dashboard package has no test runner and no test
  files; introducing vitest, jsdom and a testing-library setup to it is a
  change to the package's build and dependency surface that is not this brief's
  objective. `buildTrendPoints`, `buildCandidates` and `buildTimeline` are
  exported as pure functions specifically so they are testable the day a runner
  arrives. This is a real gap: the timeline's transition logic is the most
  intricate code in the change and it is covered only by the manual verification
  below.
- **I did not fix the pre-existing lint failure**, which is in
  `artifacts/api-server/src/lib/__tests__/emailAuthDns.test.ts`, a file I do not
  own. It failed on arrival and it fails now, identically.
- **I did not expose the archived metric snapshot payloads**, which would need a
  change to `/m365/scans/{id}`. The tab shows the key list the endpoint returns
  and labels the payloads as archived but not served.
- **I did not add a CSV export to the trend table.** `ExportBtn` exists and it
  would be a natural addition, but it was not asked for and the counts table is
  already selectable text.

### How the rendered checks were performed

There is no browser automation in this repository and I did not add any. The
tab was rendered by running the real api-server against a throwaway libsql
database, with the dashboard's own dev server proxying `/api` to it, and driving
headless Edge over the DevTools protocol from scripts held outside the
repository in a temporary directory. The database was seeded with scan runs
built from the fingerprints the running server's own findings register actually
holds, so the archive, the register and the triage state all describe the same
findings. Demonstration mode (`DEMO_MODE=healthy-mid-market`) supplied the
tenant data; the orange demonstration banner is visible in every screenshot.

#### 1. Zero, one, two and twenty scans

**Zero scans.** The tab does not render four sections each reporting nothing. It
renders one `EmptyState` with the calendar-clock icon: "No scans recorded yet /
A scan is archived each time data is collected. Press Refresh Data in the header
to record the first one; the trend and drift views appear once there are two."
The sidebar still lists the four sections, so the shape of the tab is legible
before there is anything in it.

**One scan.** Scan Runs shows the single row ("7 Aug 2026 13:19, Completed, 1m
30s, manual-refresh, 18 findings"). The trend section does not draw an axis
through one observation: it renders `SingleScanSnapshot`, a sentence ("One scan
recorded, on 7 Aug 13:19. A trend needs at least two, so this is the starting
position rather than a direction of travel.") above five count tiles reading
Critical 4, High 5, Medium 4, Low 3, Info 2. Drift renders its own empty state:
"Only one scan so far / Drift needs two completed scans. The second one,
whenever it runs, will be comparable with this one."

**Two scans.** The chart draws with two points and two axis ticks, 4 Aug and 7
Aug, one at each end. The counts table has two rows. Drift defaults to the pair
and shows Appeared 0, Resolved 0, Changed 3, the three being findings that went
Pass to Fail between the two scans.

**Twenty scans.** All twenty ticks render at 1500 px viewport width without
overlapping. This is the case the brief asked me to look at for axis
degradation, so I also rendered it at 900 px: `minTickGap={28}` with
`interval="preserveStartEnd"` thins the labels to eight — 11 Jun, 20 Jun, 29
Jun, 8 Jul, 17 Jul, 26 Jul, 7 Aug — keeping the first and last, which are the
two a reader looks for. Labels never overlap and never rotate. The counts table
keeps all twenty rows at both widths, so thinning the axis loses no data. The
seeded set includes one failed run in the middle; the trend excludes it and
prints "1 run did not complete and is excluded: a partial archive would draw a
fall that never happened," and the failed row is visible in Scan Runs with a red
Failed badge and 0 findings archived.

#### 3. Fields labelled summary-only on screen

The `SummaryOnlyNote` is rendered inside the trend, drift and per-finding
sections — inside rather than once at the top, so a reader who expands one
section and screenshots it gets the caveat in the screenshot. It names two
groups:

*Never archived* (absent from `findings_history` entirely): Description,
Remediation, Source metric, Triage state (status, owner, notes, due date), First
seen and last seen.

*Archived but not returned by the scan endpoint*: Evidence status, Confidence,
the archived metric snapshot payloads (only the list of keys is returned).

Cross-checked against the schemas: `FindingWithState` carries fingerprint,
ruleId, category, title, description, severity, checkStatus, evidenceStatus,
confidenceLabel, metricId, remediation, status, owner, stateNotes, dueDate,
firstSeen, lastSeen, stateUpdatedAt. `ScanFinding` carries fingerprint, ruleId,
category, title, severity, checkStatus. The difference is exactly the eight
items above, with `stateUpdatedAt` counted inside triage state.

Each section adds its own sentence: the trend notes that counts follow the rules
as they were evaluated at each scan, so a rule added later does not
retrospectively appear in earlier scans; drift notes that entries carry no
description, remediation or triage state; the per-finding view notes that
transitions before the oldest retained scan are unrecoverable and that the
register keeps only the latest triage change.

Individually, the `NotArchived` placeholder renders in italics with a tooltip
wherever a specific field is missing. Observed in the candidate table as "Not in
retained scans" for the 61 register findings that have no archived rows, and in
the timeline card as "No longer in the live register, so its triage state is
*Not archived*." Neither renders as a zero or an empty cell.

#### 4. Loading and error states use the shared components

Loading uses `TableSkeleton` in each section and `RefreshIndicator` at the tab
root while refetching without blanking mounted content.

To force an error I blocked only `*/api/m365/scans*` at the browser rather than
stopping the server. Stopping the server was my first attempt and it proved
nothing: the app-level onboarding gate fails first and replaces the whole
dashboard with "Unable to verify onboarding requirements", so the tab never
mounts. With only the scans endpoint blocked, the tab rendered the shared
`ErrorPanel`: amber warning triangle, "Couldn't load the scan history", the
query's message "Failed to fetch" beneath it, and a Retry button wired to the
hook's invalidate-by-prefix refetch, which re-runs the list and every detail
query together. No zeroed chart, no empty table, no healthy-looking blank.

A single scan's detail failing is handled separately and does not take the tab
down: the point becomes a gap in the line and the tab reports "N scans could not
be read and are shown as a gap in the line, not as zero."

#### 7. Greyscale

The trend view was rendered with a `grayscale(1)` filter applied to the
document, which is the transform a monochrome printer applies, on the
twenty-scan set with all five severities carrying non-zero counts.

All five series remain distinguishable:

| Series | Line | Marker |
| --- | --- | --- |
| Critical | solid | filled circle |
| High | long dash (`7 3`) | filled square |
| Medium | fine dot (`2 3`) | filled triangle |
| Low | dash-dot (`9 3 2 3`) | filled diamond |
| Info | sparse dot (`1 4`) | stroked cross |

The legend swatches are equally distinguishable in greyscale, because each draws
its own dash pattern and marker rather than relying on a colour chip.

One honest limitation. Where two series hold the same value across a stretch of
scans their lines are coincident and their markers are drawn on top of one

were indistinguishable along the baseline. That is true of any line chart and is
not fixed by dashes. It is the reason the counts table sits under the chart, and
in the table the same stretch reads unambiguously.

| Field | Bytes | Status today |
| --- | --- | --- |
| Currently archived columns, combined | 148 | archived and served |
| `evidence_status` + `confidence_label` | included in the 148 | archived, **not served** |
| `description` | 83 | not archived |
| `remediation` | 84 | not archived |
| `evidence` | 90 | not archived |
| `metric_id` | 34 | not archived |
| Triage state at scan time (estimate) | ~60 | not archived |

**The cheap half should be done and needs no schema change at all.** Evidence
status and confidence are already in `findings_history`; `GET /m365/scans/{id}`
simply does not select them. Serving them costs zero additional storage and
recovers the fields for every scan already recorded. The same is true of the
archived snapshot payloads, which are stored in full in
`metric_snapshots_history` and reduced to a key list at the route. This is the
change I would make first, and it is the one my on-screen note is careful to
distinguish so that a reader can see it is cheap.

**The other half costs about 8%.** Adding description, remediation, evidence,
metric id and the triage state as it stood at the scan is roughly 351 extra
bytes per finding per scan, so about 22 kB for a 63-finding scan. Set against
what a scan already costs:

| | Per scan | At the default 50-scan retention |
| --- | --- | --- |
| `metric_snapshots_history` (19 keys × ~14.7 kB) | ~280 kB | ~14.0 MB |
| `findings_history` today (63 × ~184 B) | ~11.6 kB | ~0.6 MB |
| **Total today** | **~291 kB** | **~14.6 MB** |
| Proposed additional finding columns | ~22 kB | ~1.1 MB |
| **Total proposed** | **~313 kB** | **~15.7 MB** |

So the archive is already dominated by snapshot payloads by a factor of about
twelve, and the finding detail everyone actually wants to read is the cheapest
thing in it. The increase is 7.6% on a store that is 15 MB at full retention on
a local file database.

My recommendation is to do it, in this order: serve what is already archived
first, since it is free; then add `description`, `remediation` and `metric_id`,
which are what make a scan-scoped view genuinely readable rather than a list of
titles; then consider the triage state, which is the one with a real design
question attached, because "the state at the time of the scan" and "the state
now" are different claims and archiving the former is the first step towards the
transition log discussed below. I would leave `evidence` until someone has a
concrete use for it, since it is the least legible field and the second largest.

Two caveats a human should weigh. The estimates come from one fixture; a tenant
with several hundred findings scales the finding rows linearly, though the
snapshot payloads scale too and stay dominant. And archiving more columns does
nothing for scans already recorded, so the benefit starts from the day it ships,
which is an argument for doing the free half now rather than bundling the two.

### The API has no aggregate endpoint for per-scan severity counts

This is the finding the brief asked me to report rather than fix. Something like
`GET /m365/scans?include=severityCounts`, or a `severityCounts` object on each
`ScanRun`, would replace N requests with one. The counts are a `GROUP BY
scan_id, severity` over a table that is already indexed by `(scan_id,
fingerprint)`, so it is cheap on the server and would remove the window control
from the tab entirely, letting the trend show the full retained history by
default. Until then, opening the tab issues one request per scan in the window.

### The API keeps no log of triage transitions

`finding_state` holds one row per fingerprint with a single `updated_at`. So
"who marked this remediated, and when, and what did they say" is answerable only
for the most recent change; every earlier one is overwritten. For a register
whose purpose is to be evidence in a client conversation, that is a gap worth a
look. A `finding_state_history` table appended to on each PATCH would make the
timeline a real audit trail rather than a timeline with one interleaved point.

### Smaller things

- **Deep-link scrolling lands partway.** Measured above; it affects existing tabs
  more than this one, so it belongs to `CollapsibleSection` rather than here.
- **The scan endpoints do not emit `collectionIssues`.** Every section passes an
  `issue` prop read the same way every other section reads it, and it is always
  null today. This is deliberate: it costs nothing and starts working the day
  the endpoints carry issues.
- **Pruning is invisible until it has happened.** `SCAN_HISTORY_LIMIT` defaults
  to 50 and older scans are deleted with their archives. The tab says older runs
  are pruned and not recoverable, but a client who expects two years of history
  from a monthly scan will get four years and a client scanning daily will get
  seven weeks. Someone should decide whether that default is right and whether
  it should be surfaced as a setting.
- **Severity values outside the five known ones** are counted and reported in a
  note rather than plotted, so they cannot silently vanish. No fixture currently
  produces one.
- **No test coverage on the timeline logic.** Repeated from "What I did not do"
  because it is the risk in this change I would most want a reviewer to weigh.
