# T10: Offline demonstration mode with fixture tenants

Read `CONTRACT.md` first. Wave 3. Estimated 4 hours. **New feature, not on the existing backlog.**

## Objective

Add a mode in which the entire dashboard runs from a recorded snapshot instead of a live Microsoft Graph connection, with a clearly visible indication that the data is not real.

## Why this is worth building

Today, seeing this tool work requires a tenant, an app registration, consented permissions and a successful collection run. That is a barrier in three separate situations that all matter:

- Demonstrating the tool to someone who has not yet granted anything. The current answer is screenshots.
- Developing or reviewing the dashboard. Every front-end change needs live credentials to see.
- Testing the dashboard. T12 has to build a test harness, and without fixtures it has to invent every response shape by hand.

The building blocks are already there. Scans are archived to `scan_runs`. Snapshots are stored. The API is fully described by a Zod spec and generated types. What is missing is a path that reads a fixture instead of calling Graph, and a way to produce a fixture from a real run.

## Work

### 1. Decide where to intercept

There are three plausible layers: replace the Graph client, short-circuit each collector, or serve the API responses from fixture files. Think about this before writing anything, and record the reasoning.

I would intercept at the Graph client. It keeps every collector, the findings engine, the drift computation, the export pipeline and the metric store on the real code path, so what you demonstrate is what the product does. Serving canned API responses is easier and demonstrates almost nothing, because it bypasses the entire product. If you disagree after reading the code, say why.

### 2. The fixture format

A directory per tenant profile under `fixtures/`, containing recorded Graph responses keyed by request. Include a manifest with a name, a description, the schema version and the date recorded.

Ship at least two profiles, hand-authored, and be honest in the report that they are synthetic:
- `healthy-mid-market`: roughly 250 users, MFA broadly enforced, decent Secure Score, a handful of low findings.
- `neglected-smb`: roughly 60 users, sparse MFA, legacy authentication present, stale app registrations with expiring credentials, several high findings.

The second one is the one that gets used. A demonstration where nothing is wrong demonstrates nothing.

**Every value must be obviously synthetic.** Fictional domain names, fictional user names, no real tenant identifiers, no plausible-looking GUIDs copied from anywhere real. Somebody will eventually open these files in the public repository.

### 3. The switch

`DEMO_MODE=<profile-name>` in the environment. When set:
- the Graph client returns fixture data instead of calling out
- no credentials are required, and onboarding gating is satisfied
- every API response carries a flag marking the data as demonstration data
- the fact is logged at startup, unmissably

When unset, behaviour must be byte-identical to today. Verify this rather than assuming it.

### 4. Make it unmistakable in the UI

A persistent banner, not a toast, not a corner badge. It must survive navigation and must not be dismissible. The failure mode this guards against is somebody screenshotting a demonstration tenant and sending it to a client as their assessment. Design against that, not against tidiness.

Take the flag from the API response, not from a build-time constant, so that a production build pointed at a demonstration server still shows it.

### 5. The recorder

`scripts/src/exportFixture.ts`: given a live collection, write a fixture directory.

It must redact by default and fail closed. Tenant identifiers, user principal names, display names, email addresses, device names and object identifiers all get replaced with generated equivalents, consistently, so that referential integrity survives. If the redactor meets a field it does not recognise, it drops the field and warns rather than passing it through.

Document loudly that a fixture recorded from a real tenant must be reviewed by a human before it goes anywhere near a commit, and add `fixtures/*/recorded-*` to `.gitignore` so a raw recording cannot be committed by accident.

## Verification

Beyond the five gate commands:

1. `DEMO_MODE=neglected-smb` with no Azure credentials whatsoever: the server starts, the dashboard loads, and all sixteen tabs render with data. List every tab and its state.
2. The findings register populates from the fixture, and the numbers make sense for the profile. Paste the summary counts.
3. A PDF and an XLSX export both generate successfully in demonstration mode.
4. With `DEMO_MODE` unset and no credentials, behaviour is identical to `main`. Show the same failure or gating you get today.
5. The banner is visible on every tab. Confirm it cannot be dismissed and survives a reload.
6. Grep the entire `fixtures/` tree for anything resembling a real tenant identifier, a real domain, or a real email address. Paste the result.
7. Run the recorder against your own synthetic fixture and confirm it round-trips.
8. Prove the redactor fails closed: feed it a field it does not know and show the field dropped and the warning raised.
