# T11: Scan history and drift timeline

Read `CONTRACT.md` first. Wave 3, after T09 has merged. Estimated 4 hours.

## Objective

The backend already archives per-scan snapshots and findings, computes drift between arbitrary scan pairs, and exposes `/m365/scans`, `/m365/scans/{id}` and `/m365/drift`. None of it is visible. Surface it as a History tab.

This is backlog 6.6.

## Why

A single scan tells a client what is wrong today. A sequence of scans tells them whether they are getting better, which is the conversation that follows an assessment and the one that justifies the next engagement. The data is already being collected on every run and thrown away at the presentation layer.

Any api-server file. Any change to the routing mechanism itself. If the API does not expose something you need, that is a finding for your report, not a licence to add an endpoint.

## Work

### 1. Read the constraint before you design

The scan archive stores summary-level rows. Most detail fields are blank, by design, in the archived snapshot. This means a scan-scoped view cannot show everything a live view shows.

You have two honest options: label scan-scoped views as summary-only, or propose archiving more columns and leave that proposal for a human. Take the first and write the second into your report. Do not silently render a blank detail field as though it were a zero, which is precisely the defect backlog item 5.8 exists to fix elsewhere.

### 2. The views

Three, in priority order. Build the first properly before starting the second.

- **Severity trend across scans.** A line per severity, one point per scan, over time. This is the view that gets screenshotted and put in a report, so it has to look right and it has to be readable in monochrome print.
- **Drift between two chosen scans.** Two selectors, then what appeared, what resolved, what changed severity. Match `computeDrift` output exactly; where your presentation aggregates, say so on screen.
- **Per-finding history.** First seen, resolved, reopened, with the manual state changes interleaved. This is the audit trail that makes the register evidenceable.

### 3. Use what already exists

Use the generated hooks from `@workspace/api-client-react`, not hand-written fetches. Use the shared loading, error and empty-state components introduced by the dashboard consistency programme. Use `CollapsibleSection` with an `issue` prop so the section status banner behaves as it does everywhere else.

If you find yourself writing a new pattern, you have probably missed an existing one. Look before you build.

### 4. Handle the empty case first

A new installation has one scan, or none. The trend view has nothing to plot and the drift view has nothing to compare. Design for that before designing for the populated case: it is what every new user sees, and an empty chart axis is a worse first impression than a clear explanation.

## Verification

Beyond the five gate commands:

1. Render with zero scans, one scan, two scans and twenty scans. Describe each. The twenty case should show whether your axis handling degrades.
2. Drift output for a chosen pair matches `computeDrift` for the same pair. Show the API response beside the rendered view.
3. Every summary-only field is labelled as such on screen. List them.
4. Loading and error states use the shared components. Force an error and describe what rendered.
5. The tab deep-links correctly under T09's routing: `/tab/history` reloads to the right place.
6. Build output shows `HistoryTab` as its own lazy chunk and the entry chunk has not grown. Paste it.
7. Print or export the trend view to greyscale and confirm the severity series remain distinguishable.
