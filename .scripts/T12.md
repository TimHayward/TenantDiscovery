# T12: Dashboard test harness

Read `CONTRACT.md` first. Wave 3, last. Estimated 3 hours.

## Objective

19,822 lines of dashboard code have no test infrastructure of any kind. Build the harness and prove it works on the highest-value paths. Do not attempt to cover the dashboard.

## Why the scope is deliberately narrow

Nobody has ever written a dashboard test here, which means every convention is unset: where tests live, how the generated React Query hooks get stubbed, how a Radix component gets driven, what a good test looks like. Those decisions are the deliverable. A hundred shallow tests written before those decisions are settled will all need rewriting.

Ten good tests and a documented pattern is a better outcome than sixty tests and no pattern.

## Out of scope

Any component source file. If a component is untestable without a change, that is a finding for your report and a follow-up ticket, not a refactor. Any api-server file.

## Work

### 1. The harness

Vitest with jsdom, Testing Library, and `@testing-library/jest-dom`. Match the api-server's vitest configuration where it makes sense, so there is one way of doing things.

Add a `test` script to the dashboard package so the root `pnpm -r run test` picks it up, and add the step to CI.

### 2. Stubbing the API

The dashboard talks to the server through generated hooks in `@workspace/api-client-react`. Do not mock the hooks. Mock the HTTP layer with MSW, so the tests exercise the generated client, the Zod parsing and the React Query caching, which is where a real regression will be.

Build the handlers from the Zod schemas in `@workspace/api-zod` so that a fixture which does not satisfy the schema fails loudly. A test suite built on response shapes that the server can no longer produce is worse than no test suite.

If T10 has landed, use its fixture profiles as the source of the response bodies rather than authoring new ones. That gives one set of example data with one place to maintain it.

### 3. What to test

Ten to fifteen tests, chosen for what they prove about the pattern rather than for coverage:

- Rendering with data, with a loading state, with an error, and with an empty response. Four tests on one tab, establishing the shape for all sixteen.
- A `DataTable` sorts by a column and the sort is reflected in the rendered rows.
- A filter narrows the rendered rows.
- `CollapsibleSection` opens, closes, and renders its status banner from an `issue` prop.
- `KPICard` renders a value, and renders the not-assessed treatment when the value is absent. That second case is the one that guards backlog 5.8.
- Tab switching preserves state, guarding T09's keep-alive behaviour.
- The export button triggers the right request. Assert on the request MSW received, not on a spy.

### 4. Write down the pattern

`docs/testing-the-dashboard.md`: where tests go, how to add an MSW handler, how to drive a Radix component in jsdom, and the traps you hit. There will be traps: Radix portals, `ResizeObserver` being absent in jsdom, Recharts refusing to render at zero dimensions. Write down what you did about each, because the next person will hit all three.

Include an explicit "do not do this" section covering mocking the generated hooks and asserting on class names.

### 5. Coverage

Report the dashboard's coverage after your changes and propose a starting threshold. It will be a low number. Say so plainly rather than choosing a subset that flatters it.

## Verification

Beyond the five gate commands:

1. `pnpm --filter @workspace/m365-dashboard run test` passes. Paste it.
2. `pnpm run test` from the root picks the dashboard tests up. Paste it.
3. Run the suite three times and confirm identical results. Flakiness introduced now becomes permanent.
4. Prove the MSW handlers validate against the Zod schemas: temporarily break one fixture, show the failure, restore.
5. Prove one test is real: temporarily break the sort implementation, show the test catching it, restore.
6. Report the run time of the dashboard suite. If it exceeds about thirty seconds, say what is slow.
7. Confirm no component source file was modified. `git diff --stat` should show only test, config and documentation files.
