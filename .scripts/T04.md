# T04: Secrets at rest and optional API authentication

Read `CONTRACT.md` first. Wave 1. Estimated 3 to 4 hours.

## Objective

Two paired security items. `onboarding-settings.json` holds an Azure client secret in cleartext with `chmod 0600` applied only on non-Windows platforms, and `metrics.db` holds full tenant personal data with no permission hardening on any platform. Separately, the API is unauthenticated by design, which is safe on loopback and unsafe the moment `ALLOW_REMOTE=true` is set.

Close both. This is backlog 2.1 and 6.4.

## Work

### Part A: at-rest protection

Write one `fileHardening.ts` module with a single exported function that takes a path and applies owner-only permissions for the current platform. Call it at file-creation time from both `setupConfig.ts` and `metricStore.ts`.

- POSIX: `chmod 0600`. `metrics.db` currently gets nothing at all; fix that.
- Windows: `icacls <file> /inheritance:r /grant:r "%USERNAME%":F` via `child_process`. Take care with quoting and with paths containing spaces. Use the array form of `execFile` rather than string interpolation into a shell.
- Handle the failure case explicitly. If hardening fails, the correct behaviour is to log a warning at `warn` and continue, not to refuse to start. A user who cannot start the tool because an ACL call failed will simply run it somewhere less safe.

Then evaluate DPAPI (`CryptProtectData`) for the secret value itself. The realistic answer is that it needs a native module, which conflicts with this project's dependency posture, and that the correct outcome is a documented decision not to do it. Write that decision and the residual risk into the README rather than adding a native dependency. If you conclude otherwise, say why in your report and still do not add the dependency; propose it.

### Part B: optional bearer token

- Generate a token at onboarding using `crypto.randomBytes(32).toString("base64url")`. Store it alongside the settings, under the Part A protection.
- Middleware that enforces it, mounted only when the bind address is non-loopback. On loopback, behaviour must be byte-identical to today. This is the single most important constraint in the task: the default developer experience must not change.
- Compare the presented token with `crypto.timingSafeEqual` against a fixed-length buffer, not with `===`.
- The token must never appear in a log line, an error message, a health response, or the pino redaction bypass. Check what the existing redaction sentinels cover and extend them.
- Exempt `/api/healthz` from authentication so a container health check still works.
- Basic rate limiting: a fixed-window in-memory counter is sufficient and adds no dependency. Apply it to the authentication path specifically, so a wrong token cannot be brute-forced, and return 429 with `Retry-After`.

### Part C: surface it

- Show the token once in the onboarding UI response when it is first generated, with a clear instruction that it will not be shown again. Do not add UI work beyond what the API response needs; the dashboard is not yours in this wave.
- Document both parts in the README's existing network exposure table, in the same register as the surrounding text.
- Add the new variables to `.env.example` with comments.

## Verification

Beyond the five gate commands:

1. Unit tests proving the hardening hook is invoked on both files, with the platform call mocked, on both platform branches.
2. Prove the loopback path is unchanged: start with default settings, `curl` a data route with no header, assert 200.
3. Prove the remote path works: start with `HOST=0.0.0.0 ALLOW_REMOTE=true`, `curl` with no header and assert 401, then with the header and assert 200.
4. Prove `/api/healthz` answers without a token in both modes.
5. Grep the full log output of a run that includes a successful and a failed authentication, and show that the token does not appear.
6. Prove the rate limit: eleven wrong tokens in quick succession, show the 429 and the `Retry-After` header.
7. On POSIX, `stat -c %a` on both files shows `600`. Paste it.
8. Confirm the secret still round-trips through save and load after the permission change.
