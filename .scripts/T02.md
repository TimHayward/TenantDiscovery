# T02: Route and store test coverage

Read `CONTRACT.md` first. Wave 1. Estimated 4 hours.

## Objective

The suite is 101 tests, all pure-logic. No HTTP route has ever been exercised. No SQLite store has been exercised against a real client. Close the two gaps that matter most, and un-skip the three finding rule groups that are currently silently untested.

## Why

`supertest` has been sitting in `devDependencies` unused since it was added. The stores carry the logic most likely to break quietly: `regenerateFindings` atomicity, `ensureFindingsCurrent` signature gating, drift computation, auto-close, pruning. A regression in any of those produces a plausible-looking findings register that is wrong, which is the worst failure mode this product has.

## Files you own

- `artifacts/api-server/src/lib/__tests__/**` (all new files, plus `findingsRules.test.ts`)
- `artifacts/api-server/src/routes/__tests__/**` (new directory)

## Out of scope

Do not edit `setupConfig.test.ts` (T04 extends it). Do not edit any non-test source file. If a route is untestable without a production change, that is a finding for your report, not a licence to refactor.

## Work

Work in this order. It is deliberate: each stage makes the next cheaper.

### 1. Store tests against in-memory libSQL

`@libsql/client` accepts `:memory:`. Build a fixture helper that returns a fresh in-memory store per test.

Cover, in `findings/store.ts`:
- `regenerateFindings` is atomic. Force a failure part-way and assert the register is unchanged rather than half-written.
- `ensureFindingsCurrent` gates on the signature. Same inputs, second call does no work. Changed inputs, work happens.
- Auto-close: a finding present in run one and absent in run two ends up closed, not deleted, with its history intact.
- Drift between two scans matches what `computeDrift` returns for the same pair.
- Manual state set through PATCH survives a regeneration.

Cover, in `scanStore.ts`:
- `recordScan` writes the run and all its history rows.
- `SCAN_HISTORY_LIMIT` pruning removes the oldest and keeps the newest.
- Reading back a scan returns what was written, including the summary-level blank fields.

Cover, in `metricStore.ts`:
- TTL expiry behaviour at the boundary.
- The data-source and confidence metadata round-trips.

### 2. Route tests with supertest

Import the Express app from `src/app.ts` and drive it. Stub the Graph layer at the collector boundary rather than mocking `fetch`, so the tests exercise the real routing, validation and serialisation.

- `GET /api/m365/findings` including the query-parameter validation added in backlog item 2.3. Assert that a bad `severity` returns 400 with the Zod error shape, not 500.
- `PATCH` on a finding: valid transition, invalid transition, unknown fingerprint, and that the response is the updated row.
- One export route end to end. Use the unicode fixture from the WinAnsi PDF crash (backlog 1.7) so the regression is pinned. Assert content type, disposition header, and that the body is a non-trivial number of bytes.
- `GET /api/healthz` and the onboarding gating routes: an ungated request when onboarding is incomplete should behave as designed, and your test should encode what "as designed" is.
- The error handler: force an unexpected throw and assert the response does not leak a stack trace or an internal path.

### 3. The three skipped rule groups

`findingsRules.test.ts` skips the security, compliance and licensing groups. Write them.

Then add a meta-test that enumerates every rule id registered in the engine and fails if any registered rule has no test. That test is the point of this stage; it prevents the gap reopening.

### 4. Coverage reporting

Add `@vitest/coverage-v8` and a `vitest.config.ts` with v8 coverage, text and lcov reporters. Report the before and after line and branch coverage for `api-server`. Do not set a threshold; propose one in your report based on what you actually achieved, and let a human set it.
