# T07: Shared UI kit and sandbox quarantine

Read `CONTRACT.md` first. Wave 2, after T01 has merged. Estimated 3 hours.

## Objective

`artifacts/mockup-sandbox` is a second Vite application carrying a parallel copy of the shadcn component set: 36 files byte-identical to their dashboard counterparts, 19 diverged. It sits in the workspace, so CI typechecks and builds it on every push, and its Radix versions are already ahead of the dashboard's.

Extract the identical components into a shared package, document the divergence rather than resolving it, and take the sandbox off the CI critical path.

## Why extraction and not deletion

Deleting the sandbox is probably the right long-term answer, but it is a product decision about whether a design scratchpad has value, and it is not reversible without effort. Extraction gets most of the benefit immediately: one copy of the components that are genuinely shared, and a written record of exactly where the two have drifted, which is the information a human needs to decide the rest.

## Files you own

- `lib/ui-kit/**` (new package)
- `artifacts/m365-dashboard/src/components/ui/**`
- `artifacts/mockup-sandbox/**`
- `pnpm-workspace.yaml` (the `packages` list only)
- `tsconfig.base.json` (path mapping only)
- `docs/ui-divergence.md` (new)
- The `import` lines in any file that references a moved component

## Out of scope

Any dependency version change (T05 owns those). `vite.config.ts` (T06 owns it). Any component's visual behaviour: this is a move, not a redesign. Deleting the sandbox.

## Work

### 1. Establish the divergence, precisely

Produce a table of every file present in both `artifacts/m365-dashboard/src/components/ui/` and `artifacts/mockup-sandbox/src/components/ui/`, marked identical or diverged, and for the diverged ones, a one-line description of the difference and a line count for the diff.

Nineteen files diverge. Some will be trivial (an import path, a formatting difference) and some will not. Classify each as trivial or substantive. This table is the most valuable output of the task and belongs in `docs/ui-divergence.md`.

### 2. Extract the identical set

Create `lib/ui-kit` following the conventions of the existing `lib/*` packages: the same `package.json` shape, the same tsconfig layout, workspace protocol dependencies.

Move the 36 byte-identical components into it. Update every import in both applications. Add the package to the workspace and to the base tsconfig path mapping.

Two things to be careful about:
- These components import a `cn` utility from a local `lib/utils`. That utility has to move too, or the kit has to take it as a dependency. Decide and be consistent.
- Tailwind class names in a package outside the application's content glob will be purged. Check both applications' Tailwind configuration and extend the content globs to cover `lib/ui-kit`. If you miss this, the build will succeed and the styling will silently disappear, which is exactly the kind of failure that survives to production.

### 3. Leave the diverged nineteen alone

Keep both copies where they are. Add a comment at the top of each diverged file in the sandbox saying that it has drifted from the dashboard's version and pointing at `docs/ui-divergence.md`. Do not attempt to reconcile them: reconciling nineteen diverged components unattended is how a design system gets silently changed.

### 4. Take the sandbox off the critical path

Keep it in the workspace so it stays installable, but stop it gating every push. The root `typecheck` script filters `./artifacts/**`; scope it so the sandbox is excluded from the default gate, and add a separate script that includes it. Run that script yourself before you finish, so you know the sandbox still typechecks today.

State clearly in your report that the sandbox is now unguarded, because that is a real cost and a human should be aware of it.

## Verification

Beyond the five gate commands:

1. `docs/ui-divergence.md` exists with all 55 shared components classified.
2. Build the dashboard and compare the output chunk sizes against your baseline. A significant change means the Tailwind content glob is wrong.
3. Run the dashboard dev server and load at least four tabs. Confirm visually that components render with styling: buttons, badges, the sidebar, a data table, a dialog. Describe what you checked. This is the check that catches a purged Tailwind class, and no automated gate will catch it for you.
4. Confirm the sandbox still typechecks under its new script.
5. Paste the count of files moved and the count of import statements rewritten.
6. Confirm zero component files were edited other than the added divergence comments. `git diff --stat` for the moved files should show pure moves.
