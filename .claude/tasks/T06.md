# T06: Bundle budget and request-path efficiency

Read `CONTRACT.md` first. Wave 2, after T01 has merged. Estimated 3 hours.

## Objective

Two related pieces of work. The front end ships a 420 KB chart chunk that defeats its own lazy tab loading, and the server repeats expensive work on the request path. Fix both, and add the budget that stops the front-end half regressing.

This closes the remainder of backlog 6.7 and all of 5.6.

## Why

The lazy tab split already works. Every tab is a `React.lazy` chunk. But `vite.config.ts` contains three lines of `manualChunks` that pull every Recharts module into a single shared `charts` vendor chunk, so the largest artefact in the entire build is a charting library that the Settings tab does not use:

```
charts-CQ7SM5zD.js   420.77 kB │ gzip: 113.54 kB
index-B6fsyx89.js    298.01 kB │ gzip:  92.28 kB
radix-BUOWyOXV.js    114.53 kB │ gzip:  36.73 kB
tables-CiUG7nTV.js    97.64 kB │ gzip:  27.56 kB
```

On the server side, a single PDF export currently evaluates the whole findings rule set twice, `getFindings` reads every row and filters severity and status in JavaScript, and `recordScan` inserts history rows one awaited statement at a time with no transaction.

## Work

### Part A: front end

Measure first. Record the full build output before you change anything.

Then rework `manualChunks`. The goal is that a tab that renders no chart does not download Recharts. Options, in the order I would try them:

1. Delete the `charts` rule entirely and let Rollup's default chunking place Recharts into the lazy chunks that import it. This may duplicate some Recharts code across several tab chunks. Measure whether the duplication costs more than the eager download saves. It usually does not, because a user visits few tabs.
2. If duplication is severe, keep a shared chart chunk but ensure it is only reachable through the lazy boundary, so it is fetched on first chart render rather than at entry.

Whichever you choose, the deciding evidence is the size of what a user downloads to see the Overview tab, and what they additionally download to reach Settings. Report both.

Check the same question for `tables` (TanStack, 97 KB) and `radix` (114 KB) and say whether the same reasoning applies. Do not change them unless the measurement supports it.

Then add a bundle budget to `ci.yml`: fail the build if the entry chunk exceeds a ceiling you set at your achieved size plus a modest margin. Write the ceiling as a named constant with a comment explaining what it is and how to change it deliberately.

### Part B: server

- `getFindings` selects all rows and filters severity, status and category in JavaScript. Push all three into the SQL `WHERE` clause with bound parameters. Use the existing binding-safety helper.
- `recordScan` inserts history rows in a loop of awaited statements. Replace with a single `client.batch(..., "write")`.
- `getExecutiveModel` calls `getFrameworkCoverage()` twice per export, and each call re-runs the full rule evaluation. Compute once per export request and pass it down.
- `SEVERITY_RANK` is defined identically in `model.ts` and `excel.ts`. Define once and import.
- The `findings.xlsx` and `evidence.xlsx` handlers are byte-identical. Either differentiate them properly, with evidence adding the evidence columns, or collapse to one handler with a route alias. Differentiating is the better outcome if the export model already carries the evidence fields; check before deciding.
- `PATCH` on a finding re-reads the entire register to return one row. Fetch by fingerprint instead.

## Verification

Beyond the five gate commands:

1. Full build output pasted before and after, with the entry chunk and total transferred size for a cold Overview visit stated explicitly.
2. State the cold-load size for Settings before and after. If it has not improved, the change has not achieved its purpose and you should say so.
3. Prove the bundle budget works: temporarily lower the ceiling below the actual size, show CI-equivalent failure locally, restore it.
4. A test with a spy proving a single export request triggers exactly one `evaluateFindings` call, where it previously triggered two.
5. A store test proving severity filtering happens in SQL. The simplest proof is that the returned row count and the statement's own reported row count agree, or an explicit assertion on the generated SQL.
6. A test proving `recordScan` issues one batch rather than N statements.
7. Confirm PATCH still returns an identical response body to before, byte for byte, for a representative finding.
8. Confirm the two xlsx routes behave as you decided, and that an existing client calling either still receives a valid workbook.
