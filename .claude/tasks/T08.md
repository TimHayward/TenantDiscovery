# T08: Per-host concurrency limiting for collection

Read `CONTRACT.md` first. Wave 2, after T01 has merged. Estimated 3 hours.

## Objective

The background refresh fans out nineteen collection tasks with no concurrency ceiling. Several of those tasks issue one request per discovered principal or device, so on a large tenant the tool generates its own 429 storm. Add a per-host limiter, and finish unifying the two collectors that still bypass the shared fetch helpers.

This is backlog 6.2 and the remainder of 5.1.

## Why

Bounded retry with `Retry-After` already exists in `graphFetchWithRetry`. That handles being throttled. It does not stop you causing the throttling. `adminExposure.ts` issues a `transitiveMembers` request per unknown principal, and `security.ts` does the same shape of thing. On a tenant with a few thousand principals, that is a few thousand concurrent requests, all of which will be throttled, all of which will then retry.

The failure mode is not an error. It is a refresh that takes an hour and produces partial data with a page of collection issues, on the largest and most important tenant you will ever demonstrate against.

## Work

### 1. The limiter

Write a small semaphore in `concurrency.ts`. No new dependency: a counter, a queue of resolvers, and an async acquire is about forty lines. Key it by host, so `graph.microsoft.com` and `api.securitycenter.microsoft.com` get separate budgets.

Default to 8 concurrent per host, tunable by `GRAPH_MAX_CONCURRENCY` and `DEFENDER_MAX_CONCURRENCY`. Wire it inside the fetch helpers in `collectionIssues.ts`, not at each call site. If it is at the call site, the next collector someone writes will forget it.

Make sure a rejection releases the permit. A limiter that leaks permits on error deadlocks the refresh, which is worse than the problem you are solving.

### 2. Honour `Retry-After` properly

`Math.min(MAX_RETRY_DELAY_MS, retryAfter)` currently caps a server-provided `Retry-After` at 30 seconds. When Microsoft Graph asks for 60, waiting 30 and retrying is not politeness, it is a second throttle. Raise the ceiling to 120 seconds for a server-provided value while keeping the existing cap for the computed backoff. Keep the jitter.

### 3. Finish the collector unification

- `licenses.ts` still uses the Graph SDK client directly with no timeout and no retry. Migrate it to `graphFetchWithRetry` so it inherits `GRAPH_FETCH_TIMEOUT_MS`, `GRAPH_MAX_RETRIES`, the new limiter and the collection-issue capture.
- `collectSecurityEstate` hand-rolls Defender token acquisition and pagination in `fetchDefenderMachinesWithDiagnostics`. Defender is a different host with a different token scope, so the shared helper probably needs a variant parameterised on base URL and scope. Add that variant rather than special-casing.

Afterwards, `grep -rn "getGraphClient().api" artifacts/api-server/src/lib/collectors` must return nothing.

### 4. While you are in `security.ts`

Backlog item 5.9: non-Entra-joined Intune and Defender devices get keys like `intune:${md.id ?? Math.random()}`. When `id` is absent, the key changes every run, so drift reports phantom device churn. Derive a deterministic fallback from a stable tuple such as name, operating system and enrolment date. If nothing stable exists, exclude the device from drift-keyed identity and record a collection note rather than inventing a key.

## Verification

Beyond the five gate commands:

1. A fixture test that fans out 100 requests and asserts in-flight never exceeds the configured ceiling. Assert the maximum observed, not just the final state.
2. A test that a rejected request releases its permit: fan out 20 where every other one throws, and assert the batch still completes.
3. A test that a server `Retry-After` of 60 results in a 60 second wait, not 30. Use fake timers.
4. `grep -rn "getGraphClient().api" artifacts/api-server/src/lib/collectors` returns nothing. Paste it.
5. A test proving two consecutive collections over identical fixture data with `id` absent produce identical device keys.
6. Confirm collection issues are still recorded on failure for both migrated collectors, with the same shape as before.
7. Run a full background refresh against a stubbed Graph and record the wall-clock time before and after. If it is materially slower, say so: a limiter trades peak throughput for reliability and you should quantify the trade rather than hide it.
