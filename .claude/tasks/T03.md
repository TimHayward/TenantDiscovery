# T03: Repository weight and data-exposure audit (report only)

Read `CONTRACT.md` first. Wave 1. Estimated 2 hours.

## Objective

Produce a decision-ready assessment of what this public repository is carrying that it probably should not, together with a prepared but unexecuted remediation. **Change nothing but documentation.**

## Why this is report-only

`attached_assets/` holds 7.2 MB of committed material, including a 5.65 MB file named `Example_M365_Tenant_Assessment_Report_15.12.2025_*.pdf` and a 396 KB spreadsheet of the same name. The repository is public.

Whether that is a problem depends on whose tenant the example describes and what was agreed with them. That is not a judgement an agent should make, and history rewriting is not an action an agent should take unattended: `git filter-repo` is irreversible for anyone who has already cloned, and it invalidates every open branch. Your job is to make the decision easy for a human, not to make it for them.

## Files you own

- `docs/audits/repository-weight-and-exposure.md` (new)
- `docs/agent-runs/T03.md` (your report)

Nothing else. No source file, no configuration file, no `.gitignore`. If you find yourself wanting to edit anything outside `docs/`, that is the signal that the finding belongs in the report instead.

## Explicitly forbidden

Do not open, extract text from, transcribe, summarise the contents of, or otherwise inspect the interior of any file in `attached_assets/`. Report on them by name, size, type and commit provenance only. If those files contain third-party tenant data, an agent reading them and writing what it found into a new markdown file makes the exposure worse rather than better.

Do not run `git filter-repo`, `git filter-branch`, `bfg`, `git rm`, `git push --force`, or any history-rewriting command. Write the commands out in the document as text for a human to run.

## Work

### 1. Inventory

Produce a table of every committed file over 100 KB: path, size, type, the commit that introduced it, and the date. Use `git rev-list --objects --all` piped through `git cat-file --batch-check` to get this from history rather than from the working tree, because a file deleted from the tip is still in the pack.

Report the total repository size, the working-tree size, and the `.git` size, and state how much of the pack is attributable to the largest ten objects.

### 2. Exposure assessment

For each large asset, state:
- what it appears to be, from its filename and file type alone
- whether it is referenced anywhere in the codebase (grep for the filename)
- whether it is needed for the build, the tests, or the documentation
- the exposure question a human needs to answer about it, phrased as a yes-or-no question

Cover `.canvas/` (436 KB) and the `Pasted-*.txt` files in the same pass. Note where two files appear to be duplicates of each other by size and name pattern.

### 3. Also assess

- `replit.md`. The backlog records it as materially wrong: claiming PostgreSQL and Drizzle where the code uses libSQL, node-cache where the code uses the metric store, ten route files where there are twenty-seven, and Zod v4 where the catalogue pins v3. Verify each claim against the current code and report which are still wrong. Do not fix it; propose whether it should be corrected or deleted, given that this is no longer a Replit-hosted project in any meaningful sense.
- Missing governance files: no `LICENSE` despite `package.json` declaring MIT, no `SECURITY.md`, no `CONTRIBUTING.md`, no `CODEOWNERS`. For a public repository whose purpose is reading Microsoft Graph with application credentials, say which of these you would prioritise and why. Draft the `SECURITY.md` content inside your audit document as a proposal, not as a committed file.
- `.replit`, `.replitignore` and the three `@replit/vite-plugin-*` dependencies. Are they still load-bearing?

### 4. Prepared remediation

Write out, as a fenced block a human can copy, the exact sequence to remove the large assets from history if that is the decision: the `git filter-repo` invocation, the force-push, what it breaks, who needs to re-clone, and how to verify afterwards. Include the reversible alternative (remove from the tip only, leaving history intact) and be clear about what that does and does not achieve.

State plainly which option you would choose and why, then stop.
